# 実機でだけ 3 面の中ボスの帯が止まる: 実験結果と考察(2026-10-13)

## 0. 前提

- **ゲーム**: MSX turboR 用のシューティング「真 零の咆哮」(ZeroNoHoukouR)。R800 で動き、ROM は 8 メガビットの ASCII8 メガ ROM。
- **症状(#1)**: 3 面の中ボス(駆逐艦 2 隻)で、艦の帯が止まり、砲身のスプライトだけが動く。
  - 艦の帯は、画面分割で R#26/R#27 を書いて横に動かしている。
  - **実機の turboR でだけ起き、openMSX(実機 BIOS)では起きない。** ビルドによって出たり出なかったりする(コードの配置しだい)。
- **実機**: ESERAM Air で ROM を流し込んでいる。読み戻した md5 は毎回一致。

### 画面分割の仕組み(`src/core/raster.c`)

- **毎フレームの合図**は、212 行目の走査線割込み(R#19)。VBLANK 割込みは切ってある。R#15 は常に 1(FH は BIOS の 0x99 読みで落ちる)。
- **分割表** `g_ras[]` の項目は `{line, reg, val, reg2, val2, ...}`。`g_ras_i` は次の添字、`g_ras_n` は本数。
- **`g_ras_tick`** は、いま R#19 に張っている行の種類(0 = 分割 / 1 = 合図 / 2 = PCM)。
- **`g_ras_ttime`** は合図の時刻。システムタイマ(E6h/E7h、1 カウント = 3.911µs)で持つ。
- **`ras_next`**
  - el = 今 − g_ras_ttime を計る。
  - 次の分割について、el ≧ (line+45)×16.25 なら「もう過ぎた」としてその場で当てる。
  - まだなら R#19 = line − 2 + g_ras_vs を張る。分割が尽きたら合図(212+vs)を張る。
- **`ras_rearm`(合図の中で呼ぶ)**: g_ras_i = 0 にして、line==0 の分割を当て、次の分割を張る。
- **`ras_isr`**
  - g_ras_tick が 0 なら、分割を当てる(`ras_apply` → `ras_next`)。
  - 1 なら合図の仕事をする(ttime = 今、JIFFY を進める、音、`ras_rearm`)。
  - 1.5 フレーム(6400 カウント)以上空いていたら、抜けた分の JIFFY と音も足す。
- **分割の割込みの中で合図の仕事をする「遅れの経路」**(本題)

```asm
00005$:                          ; 分割を処理して ras_next が合図を張った後
    ld   a, (_g_ras_tick)
    or   a
    jr   z, 00001$               ; 分割を張った → 終わり
    call _pcm_now
    ld   de, (_g_ras_ttime)
    sbc  hl, de                  ; el
    ld   de, #RAS_TICK_LATE      ; = RAS_FRAME = 4267
    sbc  hl, de
    jr   c, 00001$               ; el < 1 フレーム → まだ合図の行の手前。普通に 212 行目の合図を待つ
    ld   de, #RAS_FRAME
    sbc  hl, de
    jr   nc, 00002$              ; 2 フレーム以上遅れ → ttime = 今 で合図の仕事
    ld   hl, (_g_ras_ttime)
    add  hl, de
    ld   (_g_ras_ttime), hl      ; ★ttime = 前の合図 + RAS_FRAME
    jr   00006$                  ; 合図の仕事(JIFFY・音・ras_rearm)
```

- ★の行は、2026-10-08 に入れた修正。
  - 最終面で、遅れの経路の ttime を「今」にしたところ、次のフレームも同じ分割の位置で「前の合図から 16ms たった」と判定された。
  - その結果、合図が 18 行目の分割に居着いた。これを避けるため「前の合図 + 1 フレーム」に変えた。

### 3 面の中ボスの分割表(8 本)

| 0, 1 | 0 | R#5 = 表 A、R#26 = 0、R#27 |

| g_ras_tick | 0 | — |
| 割込み禁止中か | 否 | 否 |

### v3(実機)

## 2. 考察: はまり状態

実機は毎フレーム次の流れを繰り返している、と考えた。

1. 32 行目の分割の割込みが入る(tick=0、i=2)。
2. `ras_next` で el ≧ RAS_FRAME → 残りの分割(64〜192 行目)は全部「過ぎた」となり、その場でまとめて当たる。合図を張る(tick=1)。
3. 遅れの経路(上の asm)で el ≧ RAS_FRAME → **ttime = 前の合図 + RAS_FRAME**、その場で合図の仕事。
4. `ras_rearm` が 0 行目の 2 本を当てる。ttime からの経過が小さいので、32 行目は「まだ」と判定され、R#19 に 32 行目が張られる(tick=0、i=2)。
   ここで張った合図の R#19 は、すぐ 32 行目で上書きされるので、212 行目の割込みは来ない。
5. 次のフレームの 32 行目で 1 に戻る。

- 帯は、2 でまとめて当てた最後の分割(192 行目の設定)のまま、画面のほとんどで固定される → **症状と一致。**
- ずれ e(= 割込みの時刻 − ttime)は、1 フレームごとに (実際の 1 フレームのカウント数 P − RAS_FRAME) ずつ動く。
- 0 ≦ e < 約 1250 の間はこの状態が続く。約 1250 は、4 で 32 行目が「過ぎた」と判定されるしきい値 (32+45)×16.25 にあたる。
- ttime がタイマだけで進み、VDP の実際の走査位置と結び付いていないことが、この状態を支えている。

## 3. openMSX での再現

v4 の ROM で、中ボスの最中、合図(JIFFY の書込み)の 2ms 後に、Tcl で g_ras_ttime を 3000 カウント戻した。
これで、はまり状態の入口(e ≈ 0〜100)を人工的に作れる。

Tcl の watchpoint で JIFFY が書かれるたびに S#2 の VR を読み、帰線の中か外かを 1 秒ごとに数えた。

| RAS_FRAME | はまり状態(合図が帰線の外で来る)が続いた時間 |
|---|---|
| 4266 | 約 13 秒 |
| **4267(本番の値)** | **約 12 秒** |
| 4268 | 約 1 秒 |

補足:
- RAS_FRAME 4268 の版では、操作なしに自然に 1 回はまった。そのときの「VR → 合図」は **1585** で、実機の 1567〜1626 と一致した。
- ttime を 4267 戻した場合は、4 で 32 行目が「過ぎた」と判定され、1 フレームで抜けた。e が大きすぎると、はまり状態は続かない。
- 実験のたびに raster.c は元に戻してある(本番のソースは無変更)。

## 4. なぜ openMSX では起きないのか(推測)

- **はまった後**: 抜けないのは openMSX でも同じ(3 の表)。違いは主に**入口に来るかどうか**。
- **openMSX**
  - タイマと VDP を同じ時間軸で計算するので、両者の比は固定。
  - フレームごとのタイミングは同じパターンの繰り返しになり、「境目すれすれの判定」に当たるかどうかはビルドごとに決まる。
  - これまでのビルドは当たらない側にいた。
- **実機**
  - タイマ(S1990)と VDP は別の水晶。両者の位相がフレームごとに滑っていくので、いずれ境目に当たる。
  - さらに P と RAS_FRAME の差の向きしだいで、e が増える向きならしきい値まで何分も抜けない。
- **この推測で説明できること**
  - ビルド(配置)によって出たり出なかったりする。処理の時刻が数サイクル動き、境目との距離が変わるため。
  - RAS_FRAME 4268 の版では openMSX でも自然に入った。
- **入口のきっかけは未特定。** 候補は次の 2 つ。
  - `ras_next` の「過ぎたか」の判定(5 行手前のしきい値)。
  - PCM のサンプルの行との取り合い(`hot_pcm.s` の LEAD)。
- 実機の電池(RTC)は無関係と考えている。タイマも VDP も電池とは独立。RTC が持つ SET ADJUST(R#18)は表示位置だけ。

## 5. 修正の案(未実施)

`ras_isr` の遅れの経路で、ttime を次のように決める。

```
今:  ttime = 前の合図 + RAS_FRAME                (タイマだけで決める)
案:  ttime = 今 − (いま処理した分割の行 + 50) × 16.25   (割り込んできた分割の行 = VDP の実際の位置から逆算)
```

- 50 は 262 − 212。分割の行の位置は VDP が決めるので、ttime が「本当の 212 行目の時刻」に合う。
- その後の `ras_rearm` → `ras_next` で、32 行目は「もう過ぎた」と正しく判定されて当たる。次の 64 行目が張られ、212 行目の合図に戻る。**はまり状態は 1 フレームで抜ける。**
- 2026-10-08 の「合図が分割の位置に居着く」問題(ttime = 今 にしたせいで起きた)も、ttime が実際の位置に合うので起きない、と考えている。
- 常駐の空きは 44 バイト。行 × 16.25 の計算は `ras_next` に同じものがあるので、収まる見込み。

### 確認の手順(案)

1. openMSX で 3 の再現手順を当て、はまり状態が 1 フレームで抜けること。
2. 全面を通して、合図の抜け・PCM のスネア・最終面(分割の多い面)に悪化がないこと。
3. 実機で 3 面の中ボスと、5 面の戦艦の弾。
   #4 の「上下スクロールで敵弾の速さが違う・弾が残る」は、R#23 の帯の分割なので同じ原因の可能性が高い。
