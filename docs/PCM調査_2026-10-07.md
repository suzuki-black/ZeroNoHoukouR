# 面中の PCM スネアを「ドラムとして」鳴らすための調査（2026-10-07）

面中の turboR 内蔵 PCM スネアが、ドラムではなく「ぶっ」という低い音に聞こえる、という指摘から始めた調査の記録。
原因の測定、OSS や資料の調査、検証 ROM での実証、ゲームへ入れるための設計までをまとめる。

- 【出典】は URL の資料・ソースで確認したもの、【実測】はこのプロジェクトで測ったもの、【推論】はそれ以外。
- 測定は openMSX の実機 BIOS の機械（`My_FS-A1ST_512K`）で行った。実機の確認は 2026-10-12 以降。

---

## 1. 結論

1. **「ぶっ」の主因は送り出しの途切れ**。音の作りではない。
   いまの方式（ゲームが待っている合間に 1 サンプルずつ出す）では、面中の 8〜9 割の時間に出す機会がない。
   その間 D/A は直前の値を保ち続け、波形が階段になる。【実測】
2. **音そのもの（いまの 32ms・3996Hz のスネア）は良い**。理想の間隔で出せば、ちゃんとスネアに聞こえる。
   ユーザーの耳でも確認済み（作り直した候補の音より、いまの音が良いと判断された）。
3. **IM2 と 4 行ごとの走査線割込みで 1 サンプルずつ出せば、途切れずに出せる**。
   検証 ROM で VDP コマンドを回しながら鳴らし、理想の音と同等になることを確認した。【実測】
4. **turboR でゲーム中に PCM を一定間隔で鳴らした公開例は見つからなかった**。
   このプロジェクトが前例のない作りになる。【出典を探した結果】

## 2. 原因の測定【実測】

### 2.1 鳴った音のスペクトル（PCM チャンネルだけを録音）

| | 素材（128B） | openMSX で鳴った音（1 面） |
|---|---|---|
| 150Hz 以下の割合 | 7% | **63%** |
| 1 発の中で同じ値が続いた最長 | 0.25ms（本来の 1 サンプル） | **中央値 4.7ms、最大 12ms** |

叫び（タイトルと結果画面）は専用ループで出しているので、段差は無かった。

### 2.2 出す機会の途切れ（`pcm_service` が呼ばれた時刻を 20 秒記録）

| 場面 | 機会 | 0.25ms 超の途切れの合計 | 最長 |
|---|---|---|---|
| 1 面（戦艦） | 6,162 回/秒 | **80%** | 52ms |
| 5 面 | 1,547 回/秒 | **92%** | 64ms |
| 最終面 | 2,245 回/秒 | **94%** | 79ms |

ゲームが待っている時間は全体の 6〜20% しかない。32ms のスネアは数百 ms〜2 秒に引き伸ばされ、多くが次の拍で断ち切られる
（5 面 97/111 回、最終面 36/36 回）。

★以前「満額で鳴った割合 80〜96%」と報告していたのは「サンプルを出し切ったか」で、**時間どおりに出たかは測っていなかった**。

### 2.3 シミュレーション（記録した機会の列で `pcm.s` の判定を再現）

`300Hz 以下の割合`。シミュレータの値は、実録音（63%）と合う（61%）。

| 音 | 理想の間隔 | 1 面 | 5 面 | 最終面 |
|---|---|---|---|---|
| いまのスネア | 24% | 61% | 76% | 70% |
| 低域を抜いたクラック（4k / 8k） | 0〜1% | 54〜58% | 70〜78% | 89〜92% |
| クラップ（8k） | 0% | 54% | 67% | 92% |
| 遅れたら飛ばす（TMNT 方式） | — | 56% | 69% | 96% |

**どんな音を選んでも、どんな飛ばし方をしても、途切れがある限り崩れる**。直すべきは鳴らし方。

## 3. 調査で分かったこと

### 3.1 turboR の PCM ハードウェア

| 項目 | 内容 | 根拠 |
|---|---|---|
| 刻み | **15,700Hz**（3579545/228）。資料の 15,750Hz は誤り | 【出典】実機報告 https://github.com/openMSX/openMSX/issues/1574 |
| A5h bit0 | 1 = ダブルバッファ。書いた値は次の刻みで出る。1 段のラッチで FIFO ではない | 【出典】同上、openMSX `MSXTurboRPCM.cc` |
| A5h bit1 MUTE | 0 にすると（openMSX では）全音源が消える。**ゲーム中は 0 を書かない** | 【出典】openMSX のソース。FPGA 版は PCM だけ。実機は未確認 |
| A4h 読み | 刻みで回る 2bit カウンタ | 【出典】openMSX、OCM の `tr_pcm.v` |
| 割込み | PCM カウンタもシステムタイマ（E6h/E7h）も**割込みを出さない** | 【出典】https://msx.org/fr/node/54947?page=1 ほか |
| 出力のアナログ段 | ローパスが強く低音寄り。FS-A1ST は高音が出にくく音割れしやすい | 【出典】https://msx.org/nl/node/46704 、https://mdpc.dousetsu.com/utility/msx/mu/player/top.htm |
| WebMSX | A4h/A5h は**未実装**（書き込みは捨てられる） | 【出典】WebMSX `DeviceMissing.js` |
| BIOS PCMPLY | 割込みを止めて鳴らし切るまで戻らない | 【出典】https://map.grauw.nl/resources/msxbios.php |

★3996Hz は刻みで割り切れない（15,700 / 3,996 ≒ 3.93）。4 刻み＝ **3,925Hz** なら揺れない。【推論】

### 3.2 turboR の PCM を使ったソフトと OSS

| 例 | 方式 | 根拠 |
|---|---|---|
| Fray（turboR 版） | 処理を止めてボイスを鳴らす。BGM は頭から鳴り直す | 【出典】https://msx.org/es/node/22392 |
| Zone Terra | ゲーム中、メインループの空き時間に効果音を出す。途切れがあると評されている | 【出典】https://www.msx.org/nl/node/44871 |
| ricbit/tmnt（デモ） | 仕事を「次のサンプルに間に合う大きさ」に刻む協調スケジューラ。遅れたら飛ばして長さを保つ | 【出典】https://github.com/ricbit/tmnt/blob/master/attract.asm |
| VGMPlay（Grauw 作、sharksym 版） | IM2 と、1 フレーム 5 回の走査線割込みでタイマを作る。E6h の 64 カウント刻み（≒3995Hz）も使う | 【出典】https://github.com/sharksym/vgmplay-sharksym （`src/Interrupt.asm`、`src/timers/LineTimer.asm`、`TurboRTimer.asm`） |
| ASCII の標準ルーチン（テクニカルハンドブック） | `di` して E6h を待つ | 【出典】https://github.com/fletto2/msx-turbor-manuals |
| 『μ』（mdpc、2025） | PSG＋FM＋PCM 8 音のソフト音源 | 【出典】https://mdpc.dousetsu.com/utility/msx/mu/player/top.htm |

**走査線割込みで A4h へ 1 サンプルずつ書く公開コードは見つからなかった**。

### 3.3 走査線割込みの性質

- 表示ライン・カウンタは、上ボーダーで負の値（212 行・60Hz では −17）にリセットされ、そこから 1 行ごとに進む。
  **割込みを出せないのは上端の手前 17 行（約 1.1ms）だけ**。帰線期間の大半では出せる。
  【出典】openMSX `src/video/VDP.cc` と https://github.com/openMSX/openMSX/pull/2191 （FS-A1ST 実機の測定と一致）
- R800 では VDP のポートに触るたびに約 8µs 待たされる。割込み処理で VDP に触る回数がそのまま負担になる。
  【出典】openMSX `src/cpu/VDPIODelay.cc`
- BIOS 経由（H.KEYI）の走査線割込みは、実機で 22 行間隔が限界だった。【実測】`raster.h`

### 3.4 他機種のドライバの、重なりと切り際の扱い

大半は「即カットして頭から」（Sonic の SMPS、Mega PCM 2、ProTracker など）。
PMD の PPSDRV は旧音を別の声に逃がして指数減衰、OpenMPT は約 1ms のランプで落とす。
【出典】調査メモの各ソース（s2disasm、vladikcomper/MegaPCM、gzaffin/pmdmini `ppsdrv.cpp`、OpenMPT）

★32ms の音が 100ms 以上の間隔で重なるのは、引き伸ばされたときだけ。**時間どおりに出せれば重ならない**。

## 4. 検証 ROM（`tools/im2pcm/`）【実測】

`sh tools/im2pcm/build.sh` → `build/IM2PCM.ROM`（16KB、ROM タイプ Normal）。

- R800 / SCREEN5（212 行） / **IM2**（表 0xE100、入口 0xE2E2） / R#15 は普段 1 / VBLANK 割込み（IE0）は切る
- 走査線割込みを 4 行ごとに出し、割込みのたびに A4h へ 1 サンプル。A5h=03h（ダブルバッファ）
- 割込みが出せない上端の区間は、直前の割込みの中でシステムタイマを 65 カウントずつ待って出す
- メインは HMMM を回し続け、合間に CPU 仕事を数える。`0xE000` に 1 を書くと割込みが始まる

| 項目 | 結果 |
|---|---|
| 書き込み | 3,925 回/秒（割込み 3,685 回/秒＋上端のまとめ出し） |
| 間隔 | 185〜301µs、中央 255µs |
| 1 発の中で同じ値が続いた最長 | **0.25ms（1 サンプル分）** |
| 300Hz 以下の割合 | **30%**（理想の列のシミュレーション 24% とほぼ同じ） |
| CPU | 割込みが動いている間 30%（上端のまとめ出しの待ち 約 1ms/フレームを含む） |

## 5. ゲームの割込み禁止区間【実測】

20µs ごとに IFF を読み、区間が割込みの受付で始まったかで分けた（1 面と 5 面の戦艦区間、各 20 秒）。

| 区間 | 長さ | 新方式への影響 |
|---|---|---|
| VBLANK の割込み処理（BIOS → BGM・効果音・OPLL・キー・JIFFY） | 中央 約 0.7ms、最長 約 2ms | 作り替えが必要 |
| 走査線割込み（画面分割、BIOS 経由） | 約 0.5ms | 新しい割込み処理に統合する |
| 本体の `di`（`vdp_cmd_flush` など） | 中央 約 0.14ms | 許容範囲（ダブルバッファで吸収） |

★20µs の分解能では、短い `di` の直後に保留中の割込みが受け付けられると 1 つの区間に見える。
  区間の始まりで割込みを受け付けたかどうかで分けないと、本体の `di` を過大に数える。

## 6. ゲームへ入れる設計（案）

段階ごとに openMSX で検証してコミットする。

1. **割込みの入口を IM2 にする**（動作はいまと同じ）。割込み処理は常に見えている RAM に置く。
2. **VBLANK 割込みをやめ、画面下端あたりの走査線割込みを毎フレームの合図にする**。JIFFY は自前で進める。
   BGM・効果音・画面分割の仕切り直しは、**割込みを開けてから**実行する（二重に入らない仕掛けを付ける）。
3. **走査線の予定表を 1 本にまとめ、PCM の 4 行ごとの割込みを足す**（スネアが鳴っている 32ms だけ）。

注意点:

- 常駐の空きは 39B（SPINTEST は 6B）。割込み処理は冷たいバンクから RAM へ写す形にする。
  RAM の空き番地は実測の地図（苦労と教訓 §16-49）で確かめる。
- BIOS の割込み処理を通らなくなるので、turboR の PAUSE キーなどが効かなくなる可能性がある。
- 全場面（タイトル、面、中ボス、撃沈演出、最終面、エンディング、検証 ROM）の確認が要る。
