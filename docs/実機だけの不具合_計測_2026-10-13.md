# 実機でだけ出る不具合の計測まとめ(2026-10-13)

MSX turboR 用シューティング「真 零の咆哮」(ZeroNoHoukouR)で、**実機の turboR でだけ出て、openMSX では出ない**不具合が見つかりました。
このメモは、それを別の AI に相談するための計測記録です。**結論はまだ出ていません。**

- 実機: MSX turboR(機種は A1ST 系)。カートリッジは ESERAM Air(1MB の RAM カートリッジ)。動作は R800 モード。
- エミュレータ: openMSX(実機 BIOS の機械 `My_FS-A1ST_512K`)と WebMSX。
- ROM: 8 メガビット(1MB)のメガ ROM。C(SDCC)と Z80 アセンブラで書いています。
- 実機は 1 台だけで、計測ではユーザーが通しで遊んで画面を撮影しています。
  1 回の計測ごとに転送と撮影の手間がかかるので、**仮説を絞ってから計測 ROM を作る**方針です。

## 2. 画面分割(ラスタ)の仕組み

関係するファイル: `src/core/raster.c`、`src/include/raster.h`、`src/banked/hot_pcm.s`

- **毎フレームの合図は、212 行目の走査線割込み**です(R#19 と S#1 の FH を使用)。VBLANK 割込みは切ってあります(R#1 の IE0=0、R#0 の IE1=1)。
  割込みは IM1 で、BIOS の H.KEYI(0xFD9A)から `ras_isr` を呼びます。
- **R#15 は常に 1** にしてあります。BIOS が割込みの中で S#0 のつもりで読む 0x99 が S#1 を読むことになり、それで FH が落ちます。そのため `ras_isr` 自身はステータスを読みません。
- **分割表** `g_ras[]` は 9 バイトのエントリの並びです: `{line, reg, val, reg2, val2, pidx, pr, pg, pb}`。
  - `g_ras_n` は本数、`g_ras_i` は次に処理する添字です。
  - `g_ras_tick` は、いま R#19 に張っている行の種類です(0 = 分割 / 1 = 合図 / 2 = PCM のサンプル)。
- **合図の割込み(`ras_isr`)では次のことをします。**
  - JIFFY と音(`snd_isr`)を進めます。
  - `ras_rearm` を呼びます。これは `g_ras_i = 0` にして、`g_ras_vs = g_vscroll` を設定し、line==0 の分割をその場で当て、次の分割行を R#19 に張ります。
- **分割の割込みでは `ras_apply` を呼びます。**
  - reg/val と reg2/val2 を書き、必要ならパレットも書きます。R#23 を書いたときは `g_ras_vs` を追従させます。
  - その後 `g_ras_i++` してから `ras_next` を呼びます。
- **`ras_next` の動き**
  - システムタイマ(E6h/E7h、1 カウント = 3.911µs)で、前の合図からの経過 `el` を計ります。
  - 次の分割の行を「もう過ぎた」と判定するしきい値は (line+45)×16.25 です。過ぎていればその場で当てます。
  - まだなら R#19 = line − 2 + `g_ras_vs` を書きます(`RAS_LINE_BIAS` = 2)。
  - 分割が残っていなければ合図の 212 行目を張ります。SCREEN3 のときだけは 192 行目です。
- **1 フレームの長さ**は `RAS_FRAME` = 4267 カウント(16.69ms)です。合図が抜けたときは、時刻を見て補います。
- **PCM のスネア**が鳴っている間は、`hot_pcm.s` がサンプルの行と分割の行を比べ、近い方を R#19 に張ります。
- **0x99 への 2 バイト書込み**(値とレジスタ番号の組)は、割込みで間を割られると壊れます。そのためコードのすべての箇所で di/ei で囲む方針です。

### 3 面の中ボスの分割表(`src/banked/ovl_mb_dd.c` の `ovl_dd_split`。8 本)

| 添字 | line | 内容 |
|---|---|---|
| 0 | 0 | R#5 = スプライト表 A、R#26 = 0 |
| 1 | 0 | R#27 = うねり |
| 2 | 32 | R#26/R#27(帯の横位置) |
| 3 | 64 | 同上 |
| 4 | 96 | 同上 |
| 5 | 128 | R#5 = スプライト表 B(R#27 だけ) |
| 6 | 160 | R#26/R#27 |
| 7 | 192 | R#26/R#27 |

艦の帯は、添字 2 以降(32 行目以降)の R#26/R#27 で横に動かしています。
**この分割が効かないと、帯が止まって砲身(スプライト)だけが動きます。#1 の見た目はこれと一致します。**

## 3. 実機での切り分け(#1。3 面の中ボス)

| ビルド | 実機での 3 面の中ボス |
|---|---|
| v0.4.0 | 正常 |
| adcb885 | 正常 |
| v0.4.1 | 壊れる |
| v0.4.1 + 3f8626f | 正常(スネアの割込みでときどきワープ → 1405b2f で対処) |
| db866f1 + 3f8626f + 1405b2f | **壊れる** |
| b5 = 上から rank_init(ランキング初期化)を抜いたもの。常駐部は同一 | **壊れる** |

- **v0.4.0 → v0.4.1 の原因は特定済みです。**
  合図の行を 212 行にするか 192 行にするかの判定で、BIOS の控え RG9SAV(0xFFE8)の LN を見ていました。
  実機ではこの判定が誤るらしく(実際の値は未確認)、SCRMOD(0xFCAF)== 3 で判定するように変えました(3f8626f)。
  これで v0.4.1 は直りました。
- **db866f1 は、v0.4.1 にランキング機能を足しただけのビルドです。**
  変更は `scene.c` の 3 行、バンク 67 の追加、タイトル画面の変更だけで、**3 面の中ボスの処理には触れていません。**
  それなのに実機では壊れます。
  - rank_init を抜いた b5 でも壊れるので、ランキングの RAM 書込み(0xE0E0)が原因という線は消えました。
  - 残る候補は、**常駐コードの配置やタイミングに依存して出る不具合**です。
  - 当時の判断は「コードが数バイト動くだけで結果が変わる」でした。
- 同じ ROM を openMSX(実機 BIOS)で動かすと、どのビルドも正常です。

## 4. 計測 ROM の結果

計測 ROM は `make HWDIAG=1` でビルドします。

- **常駐コードには一切手を入れていません**(配置が変わると結果が変わるため)。
- 計測コードはオーバレイの末尾にだけ置いています。常駐部の `rom.ihx` が通常ビルドと同一であることを確認しました。
- 結果は HUD の点数の欄に出します(1 桁目 = 値の番号、残り 4 桁 = 値)。約 4 秒ごとに次の値に切り替わります。
- 計測は `ovl_dd_split` の先頭、つまり本体が毎フレーム分割表を組み直す瞬間に行います。64 フレーム分の平均です。

### v2 の結果(3 面の中ボス)

| 番号 | 値 | 実機 | openMSX |
|---|---|---|---|
| 1 | 前の合図からの経過 el(カウント) | 2439〜2977 | 同程度 |
| 2 | `g_ras_i` の平均 ×100 | **常に 200** | **395〜485** |
| 3 | 計測の瞬間に割込みが禁止されていた回数 | 0 | 0 |
| 4 | `g_ras_tick` の平均 ×100 | **0**(分割の割込みを待っている) | — |
| 5 | `g_ras_n` の最小 ×100 + 最大 | 808(表は 8 本のまま壊れていない) | 808 |

v1 も、番号 2 は実機で常に 200 でした。

### ここから言えること

- el が 2439〜2977 なので、計測した瞬間は合図からおよそ 150〜180 行後、つまり画面のおよそ 100〜130 行目あたりです。
- openMSX では、その時点で添字 4〜5 まで(32 行目と 64 行目、ときに 96 行目の分割まで)当て終えています。
- **実機では毎フレーム、`g_ras_i` が 2 のまま止まっています。**
  line==0 の 2 本は合図の中で当たっていますが、**32 行目の分割の割込みが来ていません。**
  `g_ras_tick` は 0 なので、張っているのは分割の行です。表も壊れていません。
- **それでもゲームは止まらず進みます**(JIFFY は進んでいる)。
  分割の割込みが来ないなら、合図も張り直されないはずです。にもかかわらず合図だけは来ているように見えます。この点はまだ説明できていません。考えられるのは次の 3 つです。
  - (a) 本体の誰かが R#19 を書き換えている。
  - (b) 遅れの判定が別経路で合図の仕事をしている。
  - (c) R#19 に張った値そのものがずれていて、ある時点からまとめて処理されている。
  
  なお、`g_ras_i` が 200 で止まっているのは計測の瞬間の値です。もっと後の行で処理されている可能性は残っています。

## 6. 残っている疑問と仮説の候補

1. **32 行目の分割の割込みが、実機でだけ来ないのはなぜか。**
   - R#19 に張る値は 32 − 2 + `g_ras_vs` です。`g_ras_vs` が実機でだけ想定と違う(R#23 と食い違っている)可能性があります。
     `vdp_set_vscroll` は、分割を待っている間(`g_ras_tick`=0)は R#19 を張り直しません。本体が合図と 32 行目の間に R#23 を書くと、R#23 と R#19 の関係がずれます。
   - V9958 の実機で、R#19 と R#23 を比べる仕様、または R#19 を書いたタイミングが、openMSX と違う可能性もあります。
     たとえば、表示中のその行をすでに過ぎていると、次のフレームまで来ません。
   - BIOS が H.KEYI のあとに FH をどう扱うか(R#15=1 の前提)が、実機の turboR BIOS で違う可能性もあります。
2. **配置に依存する理由**
   ランキングを足しただけで、常駐コードは数百バイト動いています。これでタイミング(R800 の命令数)が変わり、張る時刻が境界を越えた、という線があります。
   ただし openMSX では、同じ ROM でも境界を越えません。
3. **#4(敵弾の速さ)が同じ根を持つか**
   戦艦の場面も、分割と R#23 で縦スクロールしています。分割の割込みが抜けていれば、弾の見かけの動きが変わる可能性があります。

## 10. 追記: 計測 v3・v4 と openMSX での再現(2026-10-13 夕)

### v3(実機)
| 値 | 実機 | openMSX |
|---|---|---|
| 1 フレームの間に g_ras_i が変わった回数 ×100 | **0** | 600〜650 |
| g_ras_i が初めて 3 以上になった時刻 | **9999**(来ない) | 約 1180 |
| RAM 上の常駐(0x4000-0x9FFF)の 2KB ごとの検算 | **一致** | 一致 |

→ 常駐は化けていない(別 AI の 4-1 と「セグメント 4/5 の上書き」説は消えた)。割込みは 1 フレームに 1 回だけ。

### v4(実機)
合図(JIFFY の変化)の前後の状態と、S#2 の VR の立ち上がりから合図までの時間を測った。

| 値 | 実機 | openMSX(正常) |
|---|---|---|
| 合図の直前 g_ras_i×100+g_ras_tick | **200**(32 行目の分割を待っている) | 801(全部当てて合図を待つ) |
| 合図の直後 | 200 | 200 |
| VR の立ち上がり → 合図 | **1567〜1626** カウント | 28 |
| g_ras_vs と g_vscroll | 一致(31) | 一致 |

→ **212 行目の合図の割込みは一度も来ていない。毎フレーム 1 回だけ来ているのは「32 行目の分割」の割込み。**

### 仕組み(はまり状態)
1. 32 行目の分割の割込みが入る(g_ras_tick=0, g_ras_i=2)。
2. `ras_next` で el(前の合図からの経過)が RAS_FRAME 以上 → 残りの分割はすべて「過ぎた」としてまとめて当たる。合図を張る。
3. `ras_isr` の遅れの判定(el ≧ RAS_FRAME)で、その場で合図の仕事をする。**合図の時刻は「前の合図 + RAS_FRAME」**。
4. `ras_rearm` が 0 行目の 2 本を当て、32 行目を張る。合図の時刻からの経過は小さいので「まだ」と判断され、32 行目がそのまま張られる。
5. 次のフレームも 32 行目の割込みだけが来て、1 に戻る。

ずれ e(= 割込みの時刻 − 合図の時刻)は 1 フレームごとに (実際の 1 フレーム − RAS_FRAME) ずつ動く。
0 ≦ e < 約 1250(32 行目の分割が「過ぎた」と判定される手前)の間、この状態が続く。

- 実機は VDP とタイマの水晶が別なので、1 フレームのカウント数は RAS_FRAME とわずかに違う。その差しだいで、何分も抜けない。
- 帯は 32 行目でまとめて当たった最後の分割(192 行目の設定)のまま動かない → **「艦の帯が止まり、砲身だけ動く」と一致。**

### openMSX での再現
中ボスの最中、合図の 2ms 後に g_ras_ttime を 3000 カウント戻した(はまり状態の入口を人工的に作った)。

| RAS_FRAME | はまり状態(合図が帰線の外で来る)の長さ |
|---|---|
| 4266 | 約 13 秒(46〜58 秒) |
| 4267(本番の値) | 約 12 秒 |
| 4268 | 約 1 秒 |

はまり状態での「VR の立ち上がり → 合図」は **1585**(RAS_FRAME 4268 の版で自然に 1 回入ったとき)。実機の 1567〜1626 と一致する。

### 残っている問い
- 実機で最初にはまり状態に入るきっかけは未特定(配置しだいで、どこかのフレームで合図の扱いがずれる)。
- v3 の「見張りの間の g_ras_i の最大が 1」は、この筋書きと合わない。v3 の見張りのコードを疑っている(未確認)。
