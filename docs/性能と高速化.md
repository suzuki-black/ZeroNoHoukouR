## 0. 現在の結論（最新・v0.2.0 時点）

- **律速の正体は「R800 のカートリッジ ROM コードフェッチ・ウェイト」だった。** 本作のコードは
  ROM(0x4000〜)上で実行され、R800 でもコードフェッチは ROM 律速（DRAM モードは RAM データ
  アクセスしか速くしない）。海モードが敵数個で 30fps に張り付いていたのは、エンティティ数に
  比例しない「毎フレーム固定の走査コード群」を **ROM からフェッチしていた**ため。
- **解決＝§4-3 page1 動的 RAM 実行。** ゲームループのホット区間だけ page1(0x4000-0x7FFF) を
  マッパー RAM スロットへ動的に切替え、以後は同一番地・RAM フェッチで高速実行する
  （`src/core/ramexec.c`、`g_ramx_ok=1` で有効）。加えてホットな behavior/AA/当たり判定は
  page3 RAM の `hot_ram[]` へコピーして実行（`src/core/hotcode.c` / `src/banked/hot.c`）。
  結果、**計算は 1 VBLANK 内に収まり 60fps 相当の計算余力**に到達（OVER1VB 指標が 25→1）。
- **ゲーム速度がフレームレート依存だったため、安定 30fps に固定。** 最適化で 2 倍速になった
  ので、`scene.c` の SC_STAGE で `vdp_wait_frame()` を 2 回待つ固定タイムステップにして
  30fps を担保（★2 VBLANK 目＝30fps 固定）。この余力で「ジュース」（撃破スコアポップアップ、
  敵機の 8 方向スプライト化、海機の倍増など）を載せられるようになった。
- **★重要な教訓**: この結論に至るまで、CPU 側のアルゴリズム最適化（乗除算削減・走査統合・
  当たり判定 RAM 化）は**実機 FPS をほとんど動かせなかった**。本丸は「ホットコードを ROM から
  RAM へ」だった。以下 §1〜§7 はその結論に至る全調査記録（再挑戦・別 AI 相談時の一次資料）。

## 1. 実測した性能（実機turboR / openMSX）

計測は `DEBUG_FPS` ビルドの画面FPS（校正済み）と、JIFFY非依存のフレームカウンタで実施。
（`make clean && make DEBUG_FPS=1`＝画面にFPS常時表示のデバッグROM。通常 `make` はFPSコードが
一切入らず挙動・常駐サイズ不変。）

| 条件 | 実機turboR | openMSX(C-BIOS=Z80) |
|---|---|---|
| 海モード 通常（全処理ON） | **約30fps** | 約21〜26fps |
| 海モード エンティティ処理OFF（空フレーム） | **60fps張り付き** | 60fps |
| 海モード AI（更新/AA/衝突）OFF | 約60fpsへ跳ね上がり | 約30〜35fps |
| 海アニメ（sea_frame）OFF | 30fps（≒通常＝**海は主犯でない**） | 21→23（ほぼ不変） |

**解釈**:
- 空フレームが60fps＝スクロール／HUD／`vdp_wait_frame`等の固定費は軽い。
- **AIを止めると60fpsへ跳ねる＝AI（更新/AA/衝突）が主犯**（実機で確定）。
- 海モードは敵数個なのに30fps＝**エンティティ数に依らない固定的な走査コスト**が主。
- Z80(openMSX)では個別AI差は誤差程度＝**実機turboRでしか正しく切り分けられない**
  （R800はCPUが速くVDPやROMフェッチの相対比が変わるため）。
- ★この「敵数個でも 30fps＝固定コスト」という観測が、後の「ROM フェッチ律速→RAM 実行」
  仮説（§0 の結論）へ繋がった。

### 実機turboR mask別FPS（ユーザー目視・単発。ノイズあり）
`DEBUG_FPS` ビルドの M(TRIGB) キーで各 mask の FPS を読んだ値。frame時間=1000/fps は換算。

| mask | 停止対象 | FPS | frame時間 | 基準(mask0)差 |
|---|---|---|---|---|
| 0 | なし(全ON) | 30 | 33.3ms | — |
| 8 | 衝突(recount+resolve) | 53 | 18.9ms | 衝突群 ≈ 14ms |
| 16 | 描画(ent_draw_all) | 50 | 20.0ms | 描画 ≈ 13ms |
| 2 | AA | 37 | 27.0ms | AA ≈ 6ms |
| 4 | 更新(behavior) | 30 | 33.3ms | ≈ 0 |
| 1 | 海アニメ | 30 | 33.3ms | ≈ 0 |
| 31 | 全部 | 60 | 16.7ms | — |
| 14 | AA+更新+衝突 | 50 | 20.0ms | — |

（注: fpsは非加算。個別"off"差は重複するので厳密な内訳ではない。ランキングの参考。）

### openMSX(修正後・3.58MHz・連射保持) 累積disable FPS（ノイズ大）
maskを累積で立て、単調にfpsが増える想定。実際は非単調(=ノイズ)。

```
0:all-on            fps=14.3
1:+no-collision     fps=18.7   (collision off)
2:+no-draw          fps=16.7   (↓下がった=ノイズ)
3:+no-AA            fps=27.3
4:+no-update        fps=39.7   (=only sea)
5:+no-sea           fps=50.3   (=empty)
```
→ openMSX(Z80)では **update(behavior)と海の停止で大きくfpsが上がる**。実機(衝突・描画が重く、
update・海は≈0)と**傾向が逆**。両者の食い違いは「openMSX(Z80) は R800 を代表しない」の穴に該当。

## 2. 負荷の内訳（毎フレームの処理）

`stage_update`（phase0=海モード）が毎フレーム呼ぶ主な処理：

- `ent_recount_ebul()` … 敵弾数の数え直し（O(30)全走査）※現在は O(1) カウンタ化済み
- `ent_update_all()` … 全エンティティのbehavior（O(30)。砲台4基は画面外でも`bh_turret`が走る）
- `aa_update()` … **対空砲23基を毎フレーム走査**（`SHIP_NAAG=23`）。海モードでは全AA画面外で
  全部cullされる＝**丸ごと無駄**。phase1では画面内AAが発砲。
- `special_update()` … phase1のみ（海モードは即return）
- `ent_resolve_collisions()` … プールO(30)走査＋自機弾×ターゲットのペア判定
- `aa_collide()` … 自機弾収集（O(30)）＋可視AAとの座標判定
- `ent_draw_all()` … プールO(30)走査＋スプライトSAT/色書き込み

→ **毎フレーム O(30)級の全走査が5〜6回＋O(23)のAA走査**が固定で走る。海モードの30fps
（約33ms/frame）はこの固定走査群がR800でも重い、が実態に近い。**ただし後述のとおり、
実機での本当の律速は「走査回数」でなく「この固定コード群を ROM からフェッチしていること」だった。**

### combat中の実測値（openMSX・カウント系＝速度非依存）

**アクティブ実体数・当たりペア数**（プール ENT_MAX=30 走査）:
- 連射保持あり: active=10〜19、pb(自機弾)=5(上限)、tgt(戦闘機/追尾/停泊/砲台)=4〜5、
  th(自機への脅威)=0〜8。**pb×tgt ≈ 20〜25 ペア/フレーム。**
- 連射なし(素のオートプレイ): active=5〜11、**pb=0**（=当たり判定の主ループが空。測定の穴）。

**I/O書込回数/フレーム**（`debug set_watchpoint write_io`, frames=58 平均）:

| port | 用途 | 回数/フレーム |
|---|---|---|
| 0x98 | VDP データ(VRAM書込, オートインクリメント) | **117** |
| 0x99 | VDP コントロール(アドレス/レジスタ/ステータス選択) | **340** |
| 0xA0 | PSG アドレスラッチ | 31 |
| 0xA1 | PSG データ | 30 |
| — | 合計 | **519** |

補足: `vdp_cmd_wait`(CEスピン, 0x4208-0x424F)は1スピン反復あたり 0x99 を4回叩く。340の内訳
（CEスピン由来 vs sprite/SATアドレス設定由来）は未分離。

**算術ライブラリ呼び/フレーム**: `__mulint`(16bit乗算)=2.2/f、`__divsint`(符号付き16bit除算)=**0/f**
（sdiv8 で撲滅後）、`__divuint`=0.8/f。→ 戦闘中の16bit乗除算ライブラリ呼びは**ほぼゼロ**。

**色表(coltab)書込/フレーム**: `vdp_sprite_color_tab` の呼び=**66フレームで1回(≈0/f)**
（draw1のslot別色表キャッシュ slot_ctab が効いている）。

## 3. 実施した最適化（成功・失敗・見送り）

### 3-A. ★本丸: page1 動的 RAM 実行（§4-3）＋ ホットコード RAM 化

- **成果（結論）**: §0 のとおり、これが実機 FPS を動かした唯一の本丸。計算が 1 VBLANK 内に
  収まり 60fps 相当（→ 30fps 固定）。
- **機構**:
  - `hothead.s` のジャンプテーブル(1関数=3B jp)を `hot_ram[]` の実番地にリンクし、起動時に
    bank17 から `hot_ram[]`（page3 RAM）へコピー、常駐は `__naked`asm の `jp hot_ram+3*slot`
    ラッパで呼ぶ。番地二重管理を避けるため Makefile が rom.noi の `_hot_ram` 番地を hot.c の
    `--code-loc` に供給。page3 の RAM 実行枠は **0xE000(バンクデータ)が天井**で狭い。
  - さらに page1(0x4000-0x7FFF, 常駐ホットコード)を、ゲームループのホット区間だけ RAM スロットへ
    動的に切替える（`ramexec.c` の `page1_use_ram()`/`page1_use_cart()`）。バンキング(0x6000-0x7800
    レジスタ)・被弾・BGM 切替の直前は cart へ戻す。
- **★HOT_CAP の落とし穴（v0.2.0 で踏んだ）**: `hot_load()` は `HOT_CAP` バイトだけを `hot_ram[]`
  へ転写する。hot.c が肥大して HOT_CAP を超えると、(1)末尾コードがコピーされず=ゴミ実行、
  (2)はみ出しが後続の常駐グローバル(g_scene/curstage)を破壊して海イントロで暴走する。
  **ビルドは無警告で通る**のが最悪。→ 8方向スプライト化で hot.c=5199B に増え HOT_CAP=5120 を
  超過して暴走した。修正=HOT_CAP を 5312 へ拡大＋Makefile に `hot.bin > HOT_CAP でビルドエラー`
  のガードを追加。詳細は [苦労と教訓.md](苦労と教訓.md)。

### 3-B. 見た目不変・安全な高速化（採用）

ユーザ方針「1-2ms を積んで最終的に 10-20ms 削る」に沿い、微最適を実装。**挙動不変**
（描画は従来と同一を openMSX 実画面で確認）。

| 記号 | 内容 | 結果 | 効果（推計） | 備考 |
|---|---|---|---|---|
| **A1** | coltab 差分キャッシュ（`slot_ctab[]`。同一スロットに同一色表なら 16B 書込みを省く。単色書込み時は 0 で無効化） | ✅ 採用 | 弾以外の色表書込みを削減 | commit `d89b128` |
| **A6** | SAT の RAM 鏡→一括バースト（毎枚 VRAM 直書き＝毎枚アドレス設定 を `sat_shadow[128]` へ溜め、`vdp_sat_flush` で 1 回のアドレス設定＋連続バーストへ。アドレス設定 最大32回→1回） | ✅ 採用 | Z80 ~0.3ms / turboR ~0.9ms | `ent_draw_all` 専用。HUD/結果/エンディングは直接 `vdp_sprite_pos` のまま＝影響局所化。commit `d89b128` |
| **A3** | VDP コマンド発行を「R#32 から 15 本固定」に統一（LMMV 塗りは SX/SY 未使用なので固定でよい）し、OTIR→15×OUTI 直列展開 | ✅ 採用 | 毎コマンド ~45T ≒ 0.6ms（Z80） | 常駐リクレイム後に OUTI 展開を復活。commit `d89b128`/`5b58adc` |
| — | 当たり判定 `ent_resolve_collisions` の `overlap()`インライン化＋弾座標ホイスト＋X軸早期棄却 | ✅ 採用 | collisionブロック **-31.6%**（openMSX最悪ケース） | commit `a040886`。内訳: 走査8.4%/ペア処理91.6%＝走査統合は低価値 |
| — | 敵弾上限 `g_ebul`・生存砲台 `g_lturret` を O(1) カウンタ化 | ✅ 採用 | cap判定 O(30)→O(1)=**17倍** | commit `f0ddcce` |
| — | 描画最ホット `draw1` を `__naked` ASM 化（e を IY 固定でフィールド直読み） | ✅ 採用 | drawブロック **-15%**＋常駐32B減 | commit `4e8a73e` |
| — | 弾生成の符号付き16bit除算を撲滅（`dvx[dir]*spd/8` の `/8` を sdiv8=比較+シフトへ、値は同一） | ✅ 採用 | `__divsint`=0/f 確認 | commit `3b55fa0` |
| **A2** | 単色矩形の HMMV(0xC0) 化（LMMV の約2倍） | ⏸ 見送り | セットアップ専用（フレーム予算に無関係）＋常駐余地なし | 優先度低 |

**付随して削った冗長書込み（安全確認済み）**:
- `vdp_fill` の SX/SY（R#32-35）: LMMV は参照しない → 書かない
- `vdp_lmmm`(copy) の CLR（R#44）: HMMM/透過LMMM は参照しない → 書かない
- ARG（R#45）: 常に 0（BSS 初期値）→ 書かない
- SAT 予約バイト `p[3]`: BSS で 0・非0 を書く者なし → 書かない

**重要な知見**:
- **C-level の手動 hoist/インラインは SDCC の最適化に勝てない**（当たり判定で実証）。
- **が、ポインタ多用のホット関数は SDCC が構造的に非効率コード（Entity* をレジスタ保持できず
  pop/push 往復）を吐くので、`__naked` 全 ASM＋IY オフセット直読みなら大幅に勝てる**（draw1 で -15%）。
  → 残り最適化も **まず生成 ASM(build/*.asm) を精読**して SDCC の無駄を特定する方針。

### 3-C. 常駐リクレイム ―「cold const data をバンクへ」（採用・大成功）

A6 追加で常駐 _CODE が **0xA000（バンク境界）を 34B 超過**。冗長書込み削りで一旦収めたが余地が枯渇。

- **手法**: スプライトのビットマップ `pat_*`（32B×約24種＝~768B、面開始で1回 VRAM へ流すだけの
  cold data）を **bank16(`ship_render.c`) へ移設**し、常駐は薄い bcall ラッパ（`g_shipargs.mode=4`）
  だけ残す。hot な色表（`zcol`/`barrel_col`/`barrel_flash`）は常駐維持。
- **結果**: 常駐 _CODE を **約 1029B 解放**。全スプライト描画を実画面で確認、回帰なし。commit `5b58adc`。
- **なぜ低リスクか**: 既存の `draw_card_banked` 等と同じ `g_shipargs.mode` ディスパッチに mode4 を
  足すだけ。**データ移動でコード論理を跨がない**ので `__moduchar` 多重定義も起きない。
- **重要ルール**: バンク切替中も常駐(0x4000-0x9FFF)は見えたまま＝バンク関数は常駐データ/関数
  （resident_syms 経由）を読めるが、**他バンクの static シンボルは参照不可**。
- **今後の定石**: 常駐が要るときは、まずこの「cold const/コード→バンク」で空ける。

### 3-D. 失敗・撤回した最適化（重要な教訓）

- **❌ §B3 コマンドレジスタの差分発行 → 失敗・破棄**:
  前回発行値 `vdpc_last[]` と比較し、変わった分だけ R#17 オートインクリメントで発行する狙い
  （turboR では I/O 回数削減が実行時間に直結する"本命"のはずだった）。単一 writer 設計・BSS 初期
  `vdpc_valid` の安全策も入れた。**が openMSX で phase1 の海（HMMM コピー）が砂嵐状に破綻**。
  真因＝**V9938/58 のコマンドエンジンはコマンド実行中に SX/SY/DX/DY を作業カウンタとして自ら
  書き換える**ため、「前回書いた値」と「実 VDP レジスタ」が一致しない。差分発行は省略したレジスタ
  が誤値のまま次コマンドが走り破綻する。**教訓: コマンドレジスタは「書いたら VDP が消費・改変する」
  前提で毎回書く**（YMMM 撤回と同じ「残留状態依存」の系統）。読み戻さない限り差分発行は不可＝不採用。

- **❌ OTIR 化で自機影が"分身"（実機turboR固有）→撤回**（`b337e9d`→`9a3cdf0`）:
  SAT バースト `vdp_sat_flush` を OTIR(21T/byte)化したら実機で影が分身。真因＝**R800 は
  0x98(VDPデータ)への連続書込みが速すぎると V9958 の VRAM アクセス窓に追いつかず書込み欠落**。
  C ループは1バイトあたり命令数が多く自然にペーシングされ安全。openMSX(Z80)は十分遅く再現せず、
  実機依存バグがすり抜けた。**教訓: 0x98 への一括転送を OTIR/OUTI で速くしない**（0x9B 宛の
  レジスタ間接=vdp_cmd_flush は可）。得ていた draw -7.6% は放棄。

- **spawn 探索ヒントを"遅い"と誤判定して棄却→実は速い（未実装のまま）**:
  当初「別 replica 比較」で hint=36 vs walk=27 として棄却。後日**同一ビルド内 A/B で測り直すと
  hint=19 vs walk=29（-34%）**＝正しい最適化を誤って捨てていた。※純走査コスト。実 spawn は初期化
  が支配的なので総効果は小さめだが「遅い」は誤り。**未実装**。

### 3-E. 見送り（リスク階層 B 群）

「見た目は不変だがコスト/リスクが高い」施策群。turboR 実効を測る手段が得られたら再評価。

| 記号 | 内容 | 理由 |
|---|---|---|
| **§B6** | CE 待ちに CPU 仕事を重ねる（発行→純計算→待ち） | turboR のみ利得＝測定不能。海コピーと CPU 重ねは VRAM 競合（実行中に VRAM を叩くと約半速）と HUD 振動再発のリスク |
| **§D2** | 逆順 SAT で実質 16 枚/ライン | 本作は弾が散り 1 ライン 8 枚超が稀＝発動機会少。実質倍化は 30Hz ちらつきで見せる方式＝見た目重視の本作と相性が悪い |
| **A4/§B7** | 全 VDP コマンドを VBLANK 中に一括発行 | 全コマンドのキュー化＝アーキテクチャ変更（大工事） |
| **A5/§B5** | CE 待ち自前 ISR（di/ei・S#0 復帰を外す） | BIOS 割込ハンドラ自前化＝ハング/音途切れリスク（S#2 選択中の VBLANK で BIOS ISR がフラグを消せずハング）。効果も turboR 限定で測定不能 |

## 4. AI・当たり判定 高速化の定石と改善計画（一次情報＋実測）

> 「非高速モードの素の MSX ゲームが多スプライトを表示できているのに、なぜキャラの少ない turboR
> 専用機がアルゴリズム起因で低品質になるのか」を、一次情報（msx.org 開発板・Grauw・ARTRAG/Uridium・
> Transball）と本コードの実測（生成 asm）で確定し、効果順の改修計画に落としたもの。
> ★注意: 本節の「優先度 A=算術削減」は、後の実測（戦闘中の算術ライブラリ呼び ≈0/f）と §0 の結論
> （律速は ROM フェッチ）により、本件では的外れと判明している。**アルゴリズム定石の資料として残す**。

### 4-0. 結論（当時の 4 行）
1. 律速は VDP でなく AI/発砲/当たり判定の CPU コスト。しかも「ROM/RAM のどこで実行するか」でなく
   **アルゴリズムと 8/16bit の選択**が主因……と当時は考えた（→ 実際は ROM フェッチが本丸。§0）。
2. 素の MSX(Z80 3.58MHz)でも Transball は **敵32・弾4/4・爆発2・タイルアニメ64** を滑らかに回せる。
   本作は同規模以下なのに重い＝1 オブジェクトあたりのコストが過大。
3. 過大コストの正体（生成 asm 確認）: (a) 弾ごと 16bit 乗算×2＋符号付き除算×2（`emit`）/
   (b) 狙い弾ごと内積~30回（`aim_dir`）/ (c) 毎フレーム プール全走査 約6回(各O(30)) / (d) 全座標 s16。
4. Grauw らの総意＝「命令エンコード(IX→HL等)より先にアルゴリズムを削れ：対象限定・思考間引き・
   事前計算・8bit 化」。RAM 実行化は turboR の"最後の一押し"（→ 実際はこれが本丸だった）。

### 4-1. フレーム予算（なぜ数千サイクルの無駄が効くか）
- NTSC 60Hz Z80 3.579545MHz ＝ **約 59,700 T-state/フレーム**。
- MSX は **M1 サイクルごとに +1 ウェイト**（Grauw の表は M1 込み）:
  `ld a,(hl)`=8T / **`ld a,(ix+o)`=21T** / `add hl,de`=12T / `inc l`=5T / `djnz`=14|9T /
  `call`=18T / `sbc hl,de`=17T。
- **16bit 乗算(`__mulint`)≈数百T、符号付き 16bit 除算(`__divsint`)≈数百〜千T**（Z80 に乗除算命令なし）。
  → 弾1発の速度計算(乗2+除2)だけで千T級。十数発/frame で 1〜数万T＝フレームの数十%が消える。
- turboR R800 は速いが**カートリッジ ROM のコードフェッチにウェイト**（内蔵 RAM のみ高速）。
  乗除算ライブラリは ROM 常駐なので R800 でも遅いまま。→ だから「behavior を RAM 化しても不変」
  だった（時間は ROM 側の乗除算/callee にある）。★この洞察が §4-3 の page1 RAM 実行へ発展した。

### 4-2. 本コードの実測ボトルネック（生成 asm で裏取り）
全体で `__divsint`×16箇所 / `__mulint`×14箇所（多くが `fire.c` のホットパス）。
- **(a) 弾ごとの 16bit 乗算＋符号付き除算** — `fire.c` `emit`/`emit_burst`:
  `b->vx = (s16)dvx[dir]*spd/8;`（`__mulint`＋`__divsint`）を撃つたびに乗2+除2。→ sdiv8 で除算撲滅済み。
- **(b) 狙い弾ごとの内積 ~30回** — `fire.c` `aim_dir`: `dx*dvx[i]+dy*dvy[i]` を粗8＋密7≈15方向
  → `__mulint` 約30回/狙い弾（旧版64→30に半減済みだが乗算は残る）。
- **(c) 毎フレーム プール全走査 約6回**（各 O(30)）: recount/update/衝突分類/aa_collide/fire_draw/draw
  ＝約180反復/frame を「実処理の前の走査」に消費。
- **(d) 全座標が s16**: 移動・比較・当たりが全 16bit（`add hl,de`=12T, `sbc hl,de`=17T）。
  素の MSX は 8bit 画面座標が定石（`add a`=5T, `cp`=5T ＝1/3以下）。
- **既に手当て済み**: 当たり判定は対象限定＋X軸早期棄却＋overlapインライン＋弾座標ホイスト。
  敵弾数・生存砲台は O(1) カウンタ。描画は `__naked` ASM。AA/behavior は RAM 実行。

### 4-3. 外部の定石（一次情報。出典は §7）
- **オブジェクト管理**: 256整列 SoA（H=フィールド・L=ID、`ld h,f/ld l,id/ld a,(hl)`=8T、切替=`inc h`）。
  効果は限定的（IX 版99T vs HL 版96T＝数%）＝本作では優先度低。
- **座標は 8bit・画面座標で判定**（Transball）: 位置=整数8bit+小数8bit の固定小数、判定は整数8bitのみ。
- **当たり判定**: Grauw 定式 `abs(a.center-b.center) < a.extents+b.extents` を各軸（ペア固定なら extents
  和を事前計算）。ARTRAG Uridium は **1軸8bit で先に早期棄却（Y→X）**、約24〜35T/軸。対象を方向限定
  （自機弾×敵、敵弾×自機のみ）＝O(n²)排除。カスケード（粗→厳密、`squares[256]`で乗算回避）。
- **AI/思考の間引き（多数の敵を出す最大の鍵）**: ISR タイマの剰余で移動/思考/別処理をフレームまたぎ
  時分割（Metalion「Konami は賢い」）。**移動は毎フレーム・思考は数フレームに1回**（`id%4==frame&3`）、
  画面外の敵は思考スキップ。思考 1/4 間引き＝思考コスト実質 1/4。
- **弾/spawn**: 空きスロットの O(n) 全走査を避ける＝フリーリスト/空きID スタック(O(1)) or 詰め配列
  ＋swap-remove。santiontanon 目安: 弾4/4・爆発2・敵32・タイル64 で滑らか（素の MSX の現実的上限）。
- **Z80/R800×SDCC**: `__naked`＋HL 索引で 20〜40%。乗除算は事前計算/シフト加算/8bit 化で回避。
  turboR は `MULUB/MULUW` ハード乗算あり（SDCC は使わない）。**ホットコード/弾ルーチンを内蔵 RAM へ**
  （ROM フェッチ回避／GhostwriterP: 大量小型ルーチンは RAM 常駐＋即値埋め込み自己書換が特に有効）。
  **Grauw 総意（最重要）**: 「IX/IY を削るより、実行頻度を下げる/索引構造/事前計算/比較削減＝
  アルゴリズムで稼げ」。

### 4-4. 改善計画（効果の大きい順・当時の計画）
各項: 何を / なぜ効く / 効果 / リスク。★=推奨着手順。※§0 の結論により実効優先度は変動。

- **★A. `emit`/`emit_burst` の速度計算を事前計算テーブル化**（乗除算撲滅。除算は sdiv8 で対応済み。
  効果大・リスク小）。
- **★B. 思考のフレーム時分割**（`run_fire`/AI 発砲を ID 剰余で 1/2〜1/4、移動は毎フレーム維持、
  画面外は思考スキップ。効果大・リスク中＝発射レート/難易度が変わる）。
- **★C. `aim_dir` のテーブル化**（内積→8方向オクタント＋|dy|:|dx| 比表で乗算ゼロ。効果中〜大・リスク中）。
- **D. 毎フレーム プール全走査の統合**（生存インデックス詰め配列 `g_active[]` を1回生成、死亡は
  swap-remove。約6×O(30)→O(生存数)。効果中・リスク中＝stale/順序バグ注意）。
- **E. 8bit 画面座標化**（弾/敵判定を 8bit 画面座標＋8bit 小数、Uridium 方式の1軸8bit 早期棄却。
  効果中〜大・リスク大＝座標系の広域改変、段階導入必須）。
- **F. turboR: 事前計算テーブルと弾ルーチンも内蔵 RAM へ**（枠を空けてから。→ §4-3 で実現）。

**当時の推奨着手順: A → B → C → D →（必要なら）E/F。**（結果的に F=RAM 実行が本丸だった。§0）

## 5. 計測手法の失敗と教訓（最重要・再発防止）

このプロジェクトは**計測ミスを複数出した**。原因と対策：

1. **ステージ1 vs 2 の比較が、実は 1 vs 1 だった**: `g_stage_sel` を起動直後(t=2s)に poke したが
   **crt0 の BSS 初期化(_INITIALIZER copy)に上書き**され両方ステージ1をロード（結果がビット完全
   一致だったのが兆候）。→ poke は crt0 完了後かつ読取り前に行い、**必ず読み戻して検証**。
2. **FPS カウンタが実機で誤値（2〜5 と表示）**: 「JIFFY(0xFC9E)が1VBLANK=+1」前提で換算したが、
   **実機turboR では JIFFY 増分が1でないらしく狂った**。openMSX は 60Hz で偶然正しく見えすり抜けた。
   → **起動時に JIFFY 増分を実測校正**（`93f2ed8`）。JIFFY 非依存のフレームカウンタも併設。
3. **FPS 表示が画面上で壊れていた（1走査線8枚制限）**: FPS 桁をスコア/残機と同じ最上段走査線に
   置き、V9938 の 8枚/走査線制限で桁がドロップ。`peek` で内部値だけ見て「直った」と繰り返し、
   **ユーザが見る実画面を確認していなかった**。→ **別走査線へ分離**（`3fbf7aa`）。
   **教訓: 内部値(peek)でなくユーザが見る実描画・実挙動で検証する**。
4. **鉄則**: 最適化の効果測定は**「同一ビルドに新旧両方を入れ、同じ入力で連続測定(A/B)」**。
   別ビルド比較(mtime stale)・別 replica 比較(実物と差異)・poke(上書き/レース)は誤りの温床。
   **測定値が"完全一致/直感と真逆"なら測定自体を疑え**。
5. **idle で測ると当たり判定を過小評価** / **シナリオ乱数で±5msノイズ、小改善は単発では見えない**。
6. **openMSX グローバル設定の汚染**: `settings.xml` に `z80_freq=14318180`(通常の4倍) と `samples=82`
   が入っており、CPU 計算コストが4倍の余裕で隠れていた（「衝突を止めても変化なし」等はこの余裕の
   可能性）。→ 起動は必ず明示上書き:
   `-command "set samples 1024 ; set z80_freq 3579545 ; set speed 100 ; set throttle on"`。
   ※カウント系（1フレームあたりの回数）は VBLANK 同期で速度非依存なので汚染下でも妥当。
7. **オートプレイが発砲しない**: Tcl はメニュー送りに space を押すだけ＝戦闘中に自機が撃たない
   → pb=0 で当たり判定の主ループが空。連射を測るには戦闘中に **keymatrix row8 bit0 を押しっぱなし**。
8. **スピン計測(g_spin)は破綻**: vdp_wait_frame の空回り回数を「CPU 余裕の指標」にしたが、<60fps
   （計算が VBLANK 境界を跨ぐ）では無意味。combat=456 > empty=271 と逆転＝撤回済み。
9. **ブレークポイント負荷**: 毎フレーム当たる bp/watchpoint は openMSX の実時間を著しく落とす
   （emulated 計数には無害だが timeout 到達で未完了になる）。→ timeout を付け emulated 時間で割る。

## 6. 外部AI向け引き継ぎ資料（測定事実のみ・未確定事項）

> 別 AI に助力を仰ぐための事実整理。**測定した事実のみ**（推測・仮説を排す）。
> ※本節は §0 の解決前に書かれたもの。当時「未確定」だった律速は §4-3（ROM フェッチ）で解決した。

### 6-1. 環境・制約（事実）
- CPU: 実機 R800（DRAM モード, 起動時 CHGCPU 0x82）。SDCC は z80 バックエンド＝生成は Z80 命令。
- VDP: V9958、SCREEN5(GRAPHIC4)。スプライトは V9938 mode2（1走査線8枚、色は行別16Bテーブル）。
- ROM: ASCII8 MegaROM 256KB。常駐 bank0-2（0x4010-0x9FFF, 上限24KB）。RAM は page3(0xC000-0xFFFF)。
- **重大な制約: 調査 AI は R800 を一切実行できない**（openMSX に turboR ファーム ROM が無く C-BIOS は
  Z80 専用＝openMSX 実行は全て Z80 3.58MHz）。R800 実測はユーザーの実機のみ。

### 6-2. 未確定だった事（当時。§4-3 で大半が解決）
1. openMSX(Z80) と実機turboR(R800) で、サブシステム別コストの傾向が食い違う（実機は衝突・描画が
   重く update・海≈0 / openMSX は update・海が重い）。→ R800 は VDP/ROM 相対比が違うため。
2. 当たり判定の三観測が整合しない（実機 mask8 で 30→53fps＝重い / 衝突 RAM 化しても実機不変 /
   openMSX の衝突停止効果は +4fps 程度）。→ 律速が ROM フェッチだったため、RAM 化した衝突"単体"では
   frame 全体の他のホットコード(ROM)が支配して動かなかった、で概ね説明がつく（§0）。
3. 戦闘フレーム 33ms の内訳（何に何 ms）が定量未確定。§1 は目視・非加算・単発。I/O 519回/frame が
   R800 で何 ms 相当かは R800 の VDP/PSG ウェイト実値を持たないため未確定。
4. VDP ctrl 340回/frame の内訳（CEスピン由来 vs sprite/SAT アドレス設定由来）未分離。
5. 描画#2(実機13ms相当)が具体的に何のコストか未特定（色表書込≈0/f、SAT データ書込 約117/f）。

### 6-3. コード地図（番地は DEBUG_FPS ビルド時。リンクで変動する点に注意）
- 当たり判定: `entity.c` `ent_resolve_collisions`（プール分類→pb×tgt→th×player。X軸早期棄却・
  overlap インライン・全s16 座標）。
- エンティティ更新: `ent_update_all`＋behavior 群（`banked/hot.c` で RAM 実行、16bit 座標演算主体）。
- AA: `scene_stage.c` に状態、本体 `hot_aa_update`/`hot_aa_collide`（`banked/hot.c`, RAM 実行）。
- 描画: `entity.c` `ent_draw_all`（プール分類→draw1 で SAT 影を RAM へ→`vdp_sat_flush` で一括 OUT）。
  `draw1` は `__naked` asm。色表は slot 別キャッシュ(slot_ctab/slot_col)。
- 弾生成: `fire.c` `emit`/`emit_burst`（速度=`dvx[dir]*spd`→sdiv8）、`run_fire`、`aim_dir`(内積探索)。
- VDP: `vdp.c` `vdp_cmd_wait`(0x99×4のCEスピン)、`vdp_sat_flush`(SATを0x98へOUT)、`vdp_write_addr`
  (0x99×4)、`vdp_cmd_flush`(R#32-46をOUTIで0x9Bへ)。
- スクロール: `scroll.c` `draw_row`(行ごとに `vdp_copy`=VDP コマンド)。
- RAM 実行機構: `banked/hothead.s`(ジャンプテーブル), `core/hotcode.c`(hot_load/ラッパ),
  `include/hotcode.h`, `core/ramexec.c`(page1動的RAM切替), `Makefile`(hot.ihx→bin, `_hot_ram`番地供給),
  `tools/ihx2bin.mjs`。
- 起動: `core/main.c`(sys_init→hot_load→sound_init→scene_run), `core/sys.c`(R800 DRAM 切替 CHGCPU 0x82,
  version>=3のみ)。

### 6-4. 測定を再現/検証するための注意（openMSX を使う場合）
- 起動は必ず設定を明示上書き（§5-6）。fps/時間の絶対値・比率は **Z80 であり R800 ではない**点を付記。
- 戦闘の当たり判定を測るなら戦闘中に **keymatrix row8 bit0 を押しっぱなし**（連射）。
- 毎フレーム bp は重い。timeout を付け emulated 時間で割る。
- **openMSX グローバル設定(settings.xml)の変更は事前確認**（起動オプション=一時なら不要）。

## 付録: デバッグ機構（`#ifdef DEBUG_FPS`＝リリースは完全に消える）

- `make clean && make DEBUG_FPS=1` … 画面に FPS 常時表示のデバッグ ROM を生成。通常 `make` は
  FPS コード・スプライト slot 予約が一切入らず挙動・常駐サイズ不変。
- **画面表示**: 上=FPS(2桁, JIFFY 増分を起動時校正した実 FPS) / 下="MASK nn"(現デバッグマスク)。
- **M(TRIGB)キー**でマスクをプリセット巡回: `0,2,4,8,16,14,1,31`。bit1=海 / bit2=AA(aa_update+
  aa_collide) / bit4=更新(ent_update_all+special) / bit8=衝突(recount+resolve) / bit16=描画。
  `DBG_ON()` マクロで各処理を個別ゲート。値の立った bit が「停止」。
- 関連コミット: `4116510`(FPS表示) `93f2ed8`(JIFFY校正) `3fbf7aa`(表示ドロップ修正)
  `9abd3f7`(NOSEA) `608db6b`(NOENT) `9a0d2c4`/`95ffbe2`/`bea4e48`(マスク細分化)。
- 別 µs 計測: `make DEBUG_PROF=1`（S1990 タイマ自己診断）。ただし過去、この `DEBUG_PROF` の
  プロファイラ表示が page0 の炎ソースタイルを上書きして「炎 BG 文字化け」を招いた誤診がある
  （[苦労と教訓.md](苦労と教訓.md) 参照）。計測器が対象の状態を壊していないか常に疑うこと。
