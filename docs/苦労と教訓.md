## 1. 起動・初期化・リセット

### 1-1.（最重要）crt0 が BSS(_DATA) をゼロ化していなかった
- **症状**: WebMSX でステージ中に**ソフトリセット**→コナミ→CONFIG→開始 すると、カード表示後に
  ステージが始まらずタイトルへ戻る。表示も崩れる。**クリーン起動では正常**。
- **原因究明の遠回り**: 崩れたのが海帯だったので**最初は自分が入れた YMMM を疑った**（そして念のため
  撤回した）。だが**改修版でも症状が出た**ため YMMM は無罪と判明。次に「リセット後 g_scene が 0x33 の
  ゴミ値」を観測 → **crt0 の gsinit が _INITIALIZER のコピーのみで、未初期化 static(_DATA)をゼロ化して
  いない**のが真因だった。初回起動は RAM が 0 の環境で"たまたま"動き、ソフトリセットは RAM が残るため
  前フレームの state（シーン/フェーズ/画面モード追跡）が残留していた。
- **教訓**:
  - **SDCC ROM プロジェクトでは crt0 に _DATA ゼロ化を必ず入れる**（`s__DATA` から `l__DATA` を0埋め）。
    冷起動と同じ清浄な初期状態を毎起動で保証する。**最初に入れるべき土台**。
  - **表示が崩れた場所＝原因、とは限らない**。状況証拠（海帯＝YMMM）で決め打ちせず、**再現して確定
    させる**。「改修版でも同症状」という切り分けが YMMM 無罪を証明した。

### 1-2. SCREEN12→SCREEN5 復帰で R#25(YJK) が残留し海が白化
- タイトルは SCREEN12(YJK自然画)、ゲームは SCREEN5。BIOS の CHGMOD は V9958 拡張の **R#25 を管理しない**
  ため、SCREEN12 の YJK ビットが残ると SCREEN5 の表示が壊れる（海が白化）。
- **対策**: `vdp_screen5` で必ず **R#25=0** に落とす。
- **教訓**: 画面モードを行き来する設計では、**拡張レジスタ(R#25等)の残留を明示的に断つ**。

### 1-3. bank シーンの static は 0xE000 共有RAM上で残留する
- CONFIG の `g_mode`(VIEW選択) は bank6 の static で、他のバンクシーン(ship_render 等)が同じ 0xE000 域を
  使うため**残留値になり得る**。放置すると START 時 `g_view=残留` で「カードのみ→タイトル」誤動作。
- **対策**: `config_init` で `g_mode=0` を明示。**バンク共有 RAM 上の static は入場時に必ず初期化**。

### 1-4.（再発）CHGMOD が VRAMキャッシュ(海テンプレ/艦バッファB)を消し、再構築スキップで海が崩壊
- **症状**: 普通にスタート→やられて GAME OVER →タイトル→**再スタートで海が全面ノイズに崩壊**。再現性あり。
  **実機turboRでのみ発生。openMSX(C-BIOS)では再現しない**。
- **原因**: `scene_video_enter` はタイトル(SCREEN12)→ゲーム(SCREEN5)入場で `vdp_screen5`→**CHGMOD** を実行する。
  **実機turboR BIOS の CHGMOD は VRAM を広く消去し、海テンプレ(0x10000)/艦バッファB(page2/3) まで消す**。
  1周目は消去後に `prerender_ship`(=`scroll_build_sea`+艦描画)が走り再構築されるが、**同一面をやり直すと
  `rendered_stage==curstage` で prerender がスキップ**され、消えたテンプレが再構築されないまま
  `scroll_init` がコピー→海が崩壊。**キャッシュ有効フラグ(RAM)と実VRAMが CHGMOD で乖離**する穴。
- **対策**: `stage_init`(タイトル→新規ゲームの唯一の入場点=必ず画面モード往復を伴う)で **`rendered_stage=-1`**。
  入場のたびに CHGMOD 後の再構築を強制する。コストは1周目と同じ艦生成1回のみ(カード表示の裏)。
- **なぜ C-BIOS で出ないか**: C-BIOS の CHGMOD は消去範囲が狭くテンプレ領域(0x10000)に届かないため。
  **実機依存バグは C-BIOS 検証をすり抜ける**。BIOS 依存(CHGMOD/CGTABL等)の挙動差は常に疑う。
- **教訓(=1-1/1-2 の再発)**: 「一度直したリセット漏れ」と**同じクラス**(状態の残留/乖離)が**別リソース**で
  再発した。1-1 は RAM state 残留、本件は **VRAM キャッシュの有効フラグと実 VRAM の乖離**。
  - **BIOS/画面モードをまたぐ操作は、キャッシュした VRAM 資産を無効化してから再入場する**。
  - **「有効フラグ=RAM」と「実体=VRAM」を別々に持つ設計は、両者を同期させる責任を明示せよ**。
    フラグだけ生きて実体が消える経路(CHGMOD/リセット)が必ず穴になる。

## 2. ビルドシステム／ROM 配置（SDCC 固有）

### 2-1. ヘッダ依存欠落による stale-object バグ（最悪級）
- `Entity` 構造体にフィールドを追加した後、増分 `make` がそのヘッダを include する他 .c を再コンパイル
  せず、**新旧のレイアウトが混在**。フィールド offset が食い違い→メモリ破壊→`behaviors[]` 配列外
  ジャンプ→ハング。切り分けの結論は「スロット構成でも SDCC でもなく**ビルドシステム**」だった。
- **対策**: **各 .rel を全 include ヘッダ（`$(HDRS)`）に依存**させ、構造体を触ったら `make clean`。
  生成ヘッダ `assets_data.h` も `HDRS` に含める。

### 2-2. `_CODE` が `--data-loc` を超える物理衝突
- 症状＝スプライトが飛ぶ／緑ゴミ／多彩で不安定（生成 asm も VRAM も正しいのに）。→ 末端を疑う前に
  `.map` の `s__CODE`/`s__DATA` を見る（`_CODE 終端 > _DATA 開始`なら衝突）。
- **ROM では `_INITIALIZER` を ROM 側へ置かないと初期値付き static が化ける**（const は無事）。→ 初期値付き
  static を避け、`init` で実行時に書く（例: ship_render.c の rng）。バンクシーンの static も同様（gsinit されない）。

### 2-3. 常駐 24KB の天井と RAM 実行枠
- rompack が常駐(bank0-2)超過をビルドエラー化する。定数の大物（艦データ・BGM・ビットマップ・文字列）は
  バンクへ、常駐は小 RAM バッファ＋`data_read` のみ。撃破!! パネル(574B)・敵機カラー表・艦名/撃沈文を
  バンクへ退避して捻出した。
- **★HOT_CAP の落とし穴（v0.2.0 で踏んだ・超サイレント）**: §4-3 の RAM 実行コード(hot.c)は起動時
  `hot_load()` が **HOT_CAP バイトだけ** を `hot_ram[]`(常駐 _DATA 末尾)へコピーして実行する。hot.c が
  HOT_CAP を超えると (1)末尾コードがコピーされずゴミ実行、(2)はみ出しが後続の常駐グローバル
  (g_scene/curstage)を破壊 → **海イントロ開始直後(bh_fighter 初回=約40f目)に暴走**（実機 turboR=ハング／
  openMSX=スタック破壊でタイトル復帰）。**ビルドは無警告で通る**のが最悪。8方向スプライト化で hot.c=5199B
  に増え HOT_CAP=5120 を79B超過したのが実例。→ 修正=HOT_CAP を 5312 へ拡大＋Makefile の hot.bin ルールに
  `hot.bin > HOT_CAP でビルドエラー`のガードを追加。**「RAM へコピーして実行する固定枠」は中身が枠を
  超えても言語処理系は黙って通す＝枠サイズは中身サイズにビルド時ガードで縛れ**（§2-2 の _CODE 衝突と同クラス）。

### 2-4. ROM 拡張に伴う番地ずれ
- タイトル YJK 画がバンクを占有し 128KB に空きが無く、**ROM を 256KB（32 バンク）へ拡張**。この拡張や
  グローバル追加のたびに RAM 番地がずれる。→ 検証 poke の前に必ず `build/rom.map` / `.noi` で `_g_*` の
  番地を取り直す（実際に stale 番地でボスを叩いていた）。

### 2-5. SDCC の運用
- **同時 1 プロセス厳守**（連投で多重起動→スワップ地獄）。**1 関数が ~400 行/10KB を超えると `sdcc -c` が
  数十分・RSS 数 GB 爆発**（レジスタ割当が超線形）→ 関数分割。`long`(32bit)演算は +約1.7KB になるので
  16bit Bresenham で代替。
- **asm からしか呼ばれない関数（ISR 系）は SDCC の未使用除去で消える** → 非 static 化＋`.map` で存在確認。
- **`mv`/`git checkout` で戻したファイルは古い mtime を持ち込み、make が再コンパイルせず stale 成果物**に
  なる（一時改変を戻したら `touch` するか Edit で戻す、または `rm build/該当.rel`）。

## 3. 計測（プロファイル）の落とし穴

### 3-1. static変数/関数のアドレスは毎ビルドで動く
- 検証スクリプトに古い g_scene アドレスをハードコードし、**ゴミ(0xFF=65535)を読んで「機械が誤動作」と
  誤診**した。→ static アドレスは毎回 `rom.noi`(DEF行)から取り直す。読んだ値が明らかにおかしい時は
  **まずアドレスとスクリプトを疑う**。

### 3-2. Tcl `after time "...[...]..."` は登録時に評価される
- `after time $t "... [debug read ...] ..."` と**二重引用符**で書くと `[...]` が**登録時に評価**され常に
  開始時刻の値が入る。これで一度「機械がリセットしている」と**誤診**。→ **波括弧か `list`** を使う
  （`after time $t [list snap $t]`）。**測定結果がおかしいときはまず測定スクリプト自身を疑う**。

### 3-3. 単発の遠い after time が発火しない
- 遠い未来の単発 `after time` は確実には発火しない。**0.3秒ハートビートのポーリングループ**で待つ。
  周期サンプリングは相対時間で（`after time [expr {[machine_info time]+…}]` は絶対時刻誤用で発火しない）。

### 3-4. idle で測ると当たり判定を過小評価
- 自機非発砲だと自機弾が無く collide が軽く見える（13ms）。**発砲中は34msに急増**。`keymatrixdown 8 0x01`
  (SPACE)で**発砲ホールドして実プレイ条件で測る**。安定させるなら `g_invinc` を poke して不死化。

### 3-5. シナリオ乱数で±5msのノイズ、小改善は単発では見えない
- 敵撃破数/弾数の乱数でフレーム時間は±5ms揺れる。数ms の改善は単発比較では埋もれる。**構造的に確定する
  改善（実行回数半減など）は回数ベースで確定**させ、フレーム時間の単発比較に頼らない。

### 3-6. openMSX の settings.xml を壊して 0.37×激遅（別プロジェクトも巻き込み）
- **症状**: 別プロジェクトの ROM でも激遅。**原因を「CPU 負荷」と誤診**。ユーザ指摘「最新 CPU(M5 pro)で
  CPU が原因の速度低下は有り得ない」→再考。**真因**: `samples=64`（既定1024）で throttle が小さな音バッファに
  同期し 0.37× に。`throttle off` で59×出た＝CPU は無実。
- **教訓**: **openMSX のグローバル設定(settings.xml)を触るときは必ず事前共有**。一時的変更は**起動オプション**で
  行いグローバルを汚さない。`throttle off` の実測が「CPU 律速か環境要因か」の切り分けに効く。

### 3-7. 微最適化はコンパイラに勝てない
- 当たり判定内側の座標 hoist/overlap インライン化を手で入れたが**実測差ゼロ**（sdcc が既に CSE/インライン
  済み）。コード増でオーバーフロー誘発 → revert。→ **手書き微最適化でなく構造的削減（走査回数・コピー面積・
  エンティティ数）**に投資する。`--max-allocs-per-node 3000` の sdcc は既に強力。

### 3-8.（本セッション最大級の誤診）計測画面がゲーム状態(VRAM)を破壊 ― 炎BG文字化けの真犯人はプロファイラ
- **症状**: 戦艦モードで砲台/対空砲を撃破すると、炎上 BG がフォント文字に化ける。
- **私の誤診の連鎖（全部ハズレ・別 AI 往復まで浪費）**:
  1. 「`burn_bake` が直接 VRAM 書込だから走行中の海コピーと競合」→ 実は透過 LMMM(発行前に cmd_wait)で競合しない。
  2. 「海の状態機械の二重進行(H-B)/`vdp_fill` の SX/SY 残置(H-A)で座標化け」→ コード監査で否定。
  3. 「Z80(C-BIOS)で再現しない＝**R800 タイミング固有**」→ **これも誤り**（下記参照）。
- **ユーザ指摘で解決**: 「非デバッグ ROM なら実機で炎は正常」「**あなたのデバッグ処理の方に問題あるのでは**」。
  非 DEBUG_PROF の `GAME.ROM`(§4-1入り)を実機 turboR で確認 → 炎は完全に正常 ∴ **§4-1 は無罪**。
- **真因**: 炎ソースタイルは `bake_fireballs()` が **page0 の y0..31**(`FB_PAGE0_Y=0`)へ stage 開始時に1回だけ
  焼く（gameplay 中は page1 表示で隠れた保管領域。`burn_bake` は毎回ここを source に buffer B へコピー）。
  ところが **DEBUG_PROF の凍結表示 `prof_frame_end` が page0 を表示に切替え `vdp_fill(0,0,256,110,0)`＋
  `vdp_text` で y0..110 を黒塗り＋フォント文字で上書き** → 炎タイル(y0..31)がフォント文字に化ける。以後
  `burn_bake` はその化けタイルをコピー → 炎 BG が文字になる。`bake_fireballs` は stage 開始1回なので、一度
  凍結表示を出すと次 stage まで壊れ続ける（症状と完全一致）。Z80 で再現しなかったのは**FORCE_KILL 版を
  DEBUG_PROF 抜きでビルドした**からで、R800 固有だからではない。
- **修正**: `prof_frame_end` の凍結表示を **y32以降**へ移し炎タイル(y0..31)を触らない（計測ビルドのみ）。
- **教訓**: **計測器がゲーム状態(VRAM)を破壊していた古典**。「実機だけ」「Z80 で再現せず」を安易に R800/エミュ
  固有と決め打ちせず、**まず計測器・デバッグ処理自身を疑う**（3-1/3-6 と同型）。症状「炎がフォント文字になる」は
  正しく「コピー元がフォント領域を指す」を意味していた＝別 AI の SX/SY 逆算は方向として正しかったが、化けて
  いたのは**コマンドの SX/SY でなくコピー元 VRAM(page0 y0)の中身そのもの**を計測用表示コードが上書きしていた。

### 3-9. VDP-CPU並列化は「純CPU区間」の裏でだけ（ent_draw_allと重ねてはいけない）
- 炎の VDP コピーを `ent_draw_all` の前へ出して並列化を狙ったら**DRAW が約+1ms 悪化**（実測）。`ent_draw_all`は
  SAT/色を**CPU で VRAM 直書き**するため、走行中の VDP コマンドと重ねると両者が競合して**双方遅くなる**。
- **教訓**: VDP-CPU オーバーラップ(§4-1)が効くのは**VRAM に一切触れない純 CPU(＝AI 計算)の裏**だけ。VRAM を
  触る CPU 区間と VDP コマンドは重ねない。→ 炎の並列化は撤回し、海(§4-1)は AI 計算の裏に限定した。

## 4. VDP・描画の地雷

### 4-1. VDP 書き込みの原子性（＝旧版 shadow-sprite-crash の真因）
- **VDP 操作は「1 操作＝1 つの di/ei 区間」に閉じる**。レジスタ設定(0x99 の2バイト)と VRAM 書込(0x98)を
  細切れの di/ei に分けると、隙間に 60Hz BIOS 割込み(BIOS も VDP ステータスを読む)が刺さり、選択・アドレス
  ラッチがずれる。**書込回数が多いほど確率的にいつか刺さり、固着・スクロール崩壊・一瞬表示→復帰など毎回
  違う偽バグ**になる。→ 毎フレーム更新(スプライト属性＋R#23等)を全部1区間に統合。「2枚目スプライトが
  環境の壁」は誤結論で、実体はエミュ差でなく BIOS の重さの差だった。
- **`vdp_cmd_wait`(VDPコマンド完了待ち)は MSXgl 方式に一致させる**: 毎ループ di → S#2 を選び直す → R#15 を
  S#0 へ戻して ei。自己流の `while(CE){}` は R800 でグレーハングする。`xor a` 不可(RRA の carry 保持で `ld a,#0`)。
- コマンドコード: 塗り＝LMMV **0x80** / VRAM 間コピー＝LMMM **0x90** / CPU→VRAM＝LMMC 0xB0 / バイト塗り＝
  HMMV 0xC0。**HMMV は G4(2px/byte)ではバイト単位＝縞**になるので塗りは LMMV。透過 LMMM(0x98)は環境により
  `wait_cmd` で固着 → 背景を先に焼き込んで通常コピー 0x90 だけで流す。

### 4-2. 撃破!!パネルの文字が潰れる（直書きが60Hz割込と衝突）
- パネルを**per-pixel 直書き**すると走行中の VDP コマンドや 60Hz 割込と衝突して文字が潰れる。→ 旧版に倣い
  **run-length の LMMV(塗り)** で描く（連続ビットごとに vdp_fill）。「できない」で済ませず旧版ソース/文献を当たる。

### 4-3. 炎がリング直blitで256px離れた砲台にエイリアス
- 表示リングは 256px 周期＜艦 496px。炎をリングへ直接 blit すると 256px 離れた砲台に炎が乗る（手前を壊すと
  奥に半分炎）。→ 必ず **艦バッファ B 経由**（draw_row が行ごとに正位置へ写す）。

### 4-4. u8 スプライトYの折返しで幽霊表示
- スプライト Y は u8。世界アンカーの砲台などが画面上方(負の y)にある間に (u8)化で反対端へ折返し、海上に
  幽霊表示される。**y 範囲(-16..212)外は描画しない**でガード。x も 0..255 の外は描かない。

### 4-5. 停止マーカは 216(0xD8)（212ライン時）
- スプライト終端の停止マーカは **212 ライン時は 216(0xD8)**。208(0xD0)は 192 ライン用で 212 では終端に
  ならず古い残像が残る。`vdp_sprite_init` と `vdp_sprite_hide_from` を**両方 216 に統一**。

### 4-6. sprite MODE2 の R#5（属性テーブル基底）A7–A9 はオフセットでなく AND マスクで 1 必須
- 怠ると位置・パターンは正常なのに **slot8 以降が slot(N mod 8) の色に化ける**（128B ごとに色テーブルが
  ミラー）。`R#5=0xEC`→`0xEF` に。テーブル再配置時に踏みやすい。

### 4-7. スクロール R#23/R#26-27 の非対称
- **縦スクロール R#23 はスプライトにも効く**。画面固定スプライト(HUD/自機)は Y に `g_vscroll(=cam&0xFF)` を
  加算して打ち消す。**横 HW スクロール R#26/27 はスプライトに効かない**ので、背景に乗る砲塔は
  `x = ax + g_meander` で自前補正（縦は効く＝非対称）。R#27 は R#26 と逆向き:
  `frac=s&7; R#26=(s>>3)+(frac?1:0); R#27=(8-frac)&7`。R#25 bit1(MSK)で左端 8px のゴミをマスク。

### 4-8. ラスタ競合（HUD の 1px 上下振動）
- 画面最上部の HUD を重い `ent_draw_all` の後に書くと、ラスタが既に上端を通過してから属性更新され R#23 と
  ズレて 1px 上下振動する。→ **表示クリティカルな書込(R#23＋上端スプライト)はフレーム先頭で確定**、HUD は
  `ent_draw_all` より前に描く。1 走査線 8 枚制限では HUD を低 slot に置き、超過分は敵機(高 slot)を先に間引く。

### 4-9. スプライトテーブルは page0（縦スクロールで末尾が回り込む）
- 縦スクロールで page0 末尾(Y232–255)が可視域に回り込み中央に横帯のゴミが出る。→ スクロール背景は page1 に
  描き page1 を表示、スプライト表は page0 のまま非表示にする。

### 4-10. 8フレーム毎の全域再描画で約0.5秒周期のヒッチ
- 炎アニメを「8 フレーム毎に全域(14行)一括再描画」にしたら**約0.5秒周期でフレームが停まる**ヒッチ（ユーザ
  「一定間隔でフレームが停まる」）。→ **1件/フレームのラウンドロビン＋コマ変化時のみ**再描画に分散。
  **N フレーム毎の重い一括処理は周期ヒッチの元**。

### 4-11. 効果対リスクの悪い命令は使わない（YMMM・差分発行）
- **YMMM(0xE0)** は速い(64cyc/px)が「DX から画面端まで」で残留 VDP 状態に敏感。WebMSX のソフトリセット後に
  海帯が崩れた。効果−0.8ms に対しリスクが見合わず**撤回**。艦と同じ HMMM が安全。
- **コマンドレジスタの差分発行(§B3)は破綻**: 「R#32-46 を前回書いた値と比較し変わった分だけ発行」を試作したが
  phase1 の海(HMMM コピー)が砂嵐状に破綻。**真因**: V9938/58 のコマンドエンジンはコマンド実行中に SX/SY/DX/DY
  を作業カウンタとして自ら書き換えるため、「前回書いた値」と「実 VDP レジスタ」が一致しない。→ **コマンド
  レジスタは「発行後に VDP が消費・改変する」前提で毎回書く**（読み戻さない限り差分発行は不可）。YMMM と同じ
  「残留状態依存」の系統。

### 4-12. 透過演出の残像・位置補正・256行回り込み（炎上スペクタクルの土台）
- **透過演出の残像**: 非 0 画素しか上書きしないため、動く部品が前フレームと違う位置に出ると前画素が飛び火する。
  対策＝毎フレーム同一の「覆う土台」(半径 r の塗り円)を先に描き、動く部品を半径 r 以内に収める（火球を丸く
  したのもこの流儀。四角い塗りは違和感で却下）。
- **火球の位置補正**: パターン面 page0 の点 (Px,Py) は画面上で `(Px+weaveX, Py-scrolled)`。自機(画面固定)に
  出すには逆補正。自機死亡時はスクロールをリセットしない(死んだ場所が分からなくなる)。
- **page0＝256 行の回り込み**: 艦は 496 行だが page0/リングは 256 行。演出ボックスが上下端を跨ぐと mod256 で
  反対側へ回り込む → スキップせず**ハミ出す行だけ分割してクリップ**。

### 4-13. 海／擬似多重スクロールの前提（本作 SEA13）
- **カラーサイクリング海は不向き**（同じ壁を 2 回踏んだ）: 青 3 色パレット回転は「チカチカ」になり、MSX2
  16 色が満杯で海地色を回す機構自体が不適。打ち止め。
- **横帯スプリット(R#19 ライン割込)は原理的に無効**: 海は左右の縦コラム／艦は全高＝どの走査線も艦＋海が
  混在し、縦コラム分割手段が VDP に無い。→ 成立ルートは案 13＝「in-place・海コラムのみ・艦不可侵・跳びを
  粗ノイズで隠す」＝本作の `sea_frame`。

### 4-14. 文字は BIOS CGTABL に依存しない自前フォント
- C-BIOS は CGTABL が不安定で実機とも食い違う。BIOS フォント流用は「タイトルとも旧版とも書体が違う」退化に
  なった(0 が丸 o に見える等)。→ 自前 8×8 fontset を常駐に持ち、テキスト描画と HUD 数字を同一書体で統一。

## 5. R800 の ROMフェッチ律速と §4-3（page1 動的RAM実行）

turboR の R800 は DRAM モードでも、**カートリッジ(ROM)からのコードフェッチが内蔵 RAM 実行の約3.8倍遅い**
（実機 S1990 タイマで実測）。戦闘の処理落ちは最終的にここへ収束し、「常駐ホットコードを RAM で実行する」のが
本命の対策になった（詳細な調査は [性能と高速化.md](性能と高速化.md)）。だが MSX 固有の壁がいくつもある。

- **ASCII8 バンキングとの衝突**: バンク選択レジスタ(0x6000/0x6800/0x7000/0x7800)は **page1** にある。page1 を
  RAM スロットへ切替えると、その間はバンク切替が書けない(RAM に書くだけ)。→ **ホット区間は `data_read`/
  バンク切替を一切呼ばない**設計にし、`page1_use_ram()`/`page1_use_cart()` で区間を挟む。区間内で唯一
  バンクする `bgm_play`(艦出現時1回)だけ一瞬 cart へ退避する。
- **"足元を切替える"問題**: page1 のコードを実行しながら page1 スロットを差し替えるため、切替ルーチンは
  **page3(RAM)へ退避したコピーから実行**する(`ramexec.c` の blob)。RAM 複製は ROM とバイト同一なので、
  切替後も同一番地で実行が継続できる。ENASLT(0x0024)で拡張スロットにも対応。
- **安全側フォールバック**: 空きセグメントが実 RAM かを起動時にプローブし、非対応/失敗なら**何もしない
  ＝ROM のまま**(`g_ramx_ok=0`)。C-BIOS(MSX2+)も slot1=cart/slot3=RAM/標準マッパーなので**同じ経路で動き、
  openMSX で正当性検証可能**（速度差は turboR のみ・挙動は不変）。
- **hot_ram とジャンプテーブル**: behavior/AA/衝突のホットは page3 RAM の `hot_ram[HOT_CAP]` へコピーして実行。
  枠超過は §2-3 の HOT_CAP 罠に直結する。
- **計測知見**: `ent_draw_all` 等が RAM 実行化して DRAW 約-2ms、1 VBLANK 超フレームが激減(OVER1VB 25→1/60)。
  → 60fps 相当に到達し、ゲーム速度がフレームレート依存だったため安定 30fps 固定にした(§8 の「速すぎ」参照)。

## 6. 音

- **環状シーケンサの 1 音目スキップ**: 「`trem==0` なら *先に* idx を進めてから鳴らす」実装なので、再生開始時
  idx を `n-1` で初期化しないと最初の tick で 0→1 になり毎回 1 音目が欠ける(タイトルで発覚)。melody/bass/drum
  全 voice で `idx=n-1`(drum は 15)。
- **`bgm_stop` は noise(C) も消す**。melody/bass だけ消すと直前ドラムの音量が残り「さーー」と鳴り続ける
  (開始カードの無音時に顕在化)。noise(chC)も明示的に 0 にする。
- **効果音がメロディを消す（メロディ死守）**: 自機発射音/被弾音を **tone A(メロディと同じ ch)** で鳴らして
  いたため、撃つ/被弾のたびにメロディ(A)が譲って消えていた。自機は撃ちっぱなし＝**全ステージで発生**(3面で
  目立って気づいたが実態は全面)。PSG は 3ch しか無く効果音は必ず 1ch 奪うので、**発射音/被弾音をベース側
  (tone B)へ移し、メロディ(A)は効果音に一切譲らない**設計へ(ベース/ドラムが譲る)。★"どの ch を犠牲にするか"は
  音楽上の優先度で決める＝**メロディ最優先**。

## 7. 誤診しないための姿勢（メタ教訓・横断で最重要）

- **不具合を CPU/エミュのせいにしない**。砲塔が三角・自機暴走・ハングを R800 やエミュのせいにしてワーク
  アラウンドを積み、堂々巡りで大量のトークンを浪費した(ユーザに繰り返し指摘された)。エミュ差/CPU 差に見える
  現象もほぼ**自分のコードが正しい作法を外している**のが真因。
  1. まず自コードの誤りを疑う
  2. 実在の動作コード(Fusion-C, MSXgl, libmsx)と 1 対 1 で突合する
  3. **背理法: 市販 ROM が同じ機能で動くなら 100% 自分のバグ**
  4. ワークアラウンドを積む前に、正しい作法を 1 つ見つける
- **「本当にそれが真の原因か？」を疑う**。「海が本当に遅い真の原因か？」というユーザ指摘が区間切り分け
  (VDP 律速 vs CPU 律速)につながった。
- **測定結果がおかしいときは、まず測定スクリプト自身を疑う**(3-1, 3-2)。**計測器がゲーム状態(VRAM)を破壊し得る**
  (3-8 の炎 BG 化けの真犯人はプロファイラ)。
- **状況証拠で決め打ちせず、再現して確定させる**(YMMM 無罪の切り分け＝1-1)。
- **サイレント誤変換＝最悪**。未知の値/シンボルを無診断でフォールバックせず、ツール(`gen_assets.mjs` 等)は
  範囲外値を `throw` させる運用にする。
- **できないで済ませず、旧版ソースや技術文献(Grauw/MSX.org/Konamiman)を当たる**。

## 8. 仕様・移植・進め方

- **明示指示を勝手な解釈で拡張しない**（タイトル表記で叱責された）。要件は文字通り実装する。
- **旧版機能の移植は先に旧版実装を精読**してから（憶測で作ると劣化移植になる。順序・鳴り物・表示ページ・裏で
  走る準備まで正確に把握。開始カード＋ファンファーレを旧版を見ずに作り 2 回やり直した）。**プロトのプロトより
  劣化させない＝旧版に在った機能は落とさない**（8方向スプライトも旧版にあったので v0.2.0 で移植・復活）。
- **敵が画面切替で唐突に消える** → `ent_clear` で瞬間消去せず**自然に飛び去らせる**（spawn ゲートで新規湧きは
  止まるので艦の上に湧く心配はない）。
- **入力再現の罠**: コナミの最終キー A(TRIG) は、タイトルでは**ステージ開始も兼ねる**ため、リセット後の
  自動再現でステージが始まってしまい再現がずれた。
- **タイトル(SCREEN12 YJK)の合成文字**: YJK は 4px を 1 グループ(共有の色差 J,K ＋各画素の Y)で持つ。合成文字
  (改・KAI)を重ねる際は**変更した 4px グループのみ再エンコード**し原画のクオリティを保つ。原画は
  `assets/title_base.yjk` に固定、`tools/gen_title.py` が冪等に再生成。
- **スクロールする大量文字(エンディングのクレジット)**: 毎フレーム直接描くとバースト負荷で処理落ち → 全行を
  最初に一度だけ画面外バッファへ描き、スクロール中は高速 LMMM 1 発で 1 行ずつ流す(`draw_row` と同じ流儀。
  ただしバッファ B は 31 行上限なので長いクレジットは 1 文字/フレーム先読み描画で対応)。
- **高速化で"速すぎて遊べなく"なった（フレームレート依存の罠）**: ゲーム速度(敵速/弾速/スクロール/spawn/
  アニメ)が**すべてフレーム数指定＝フレームレート依存**だったため、§4-1/§4-3 で 60fps 化した瞬間に**全部が
  2倍速**になった。対策は固定タイムステップ(ステージのみ 2 VBLANK 待ち＝安定 30fps)。速くする前に「その速度は
  フレームレートに依存していないか」を意識する。60fps で遊ばせたいなら全速度定数を 1/2 へ。
- **入力は GTSTCK 禁止**（BIOS キー走査が割込み依存で、GTSTCK+DI はフリーズ/dir=8 へ流れ続ける）。keymatrix を
  PPI 直読み(選択＋読みの 2 命令だけ短く DI→即 EI)。

## 9. 検証環境（openMSX headless）の罠と運用ルール

- 検証機は **C-BIOS_MSX2+ ＝ Z80 3.58MHz**（turboR/R800 でない、turboR ROM 未同梱）。速度は実機ターゲット
  (R800)より悲観的。最終的なタイミングは実機で要確認。**実機依存バグ(CHGMOD/OTIR 分身/炎 BG 等)は C-BIOS を
  すり抜ける**。
- **`pkill -f openmsx` を使わない**。別プロジェクトの計測実行を巻き込んで壊す。後始末は**自分のセッションの
  スクリプトパス(スクラッチのセッション UUID)で絞る**（`pkill -f "<session-uuid>"`）。計測スクリプトは
  スクラッチディレクトリに置く(`-script` のパスに UUID が入り絞り込みが効く)。
- **`timeout` を必ず付けて起動**（`exit` に到達しなくても置き去りにならない）。**グローバル設定(settings.xml)の
  変更は事前確認**。一時変更は起動オプションで。
- **`puts` は stdout に出ない** → `open ... w` でファイル出力。proc 内で file 書込するなら global 宣言。
- **PSG レジスタの debuggable 名は `"PSG regs"`**（× "PSG registers"）。VRAM は `debug read VRAM`、メモリは
  `debug read memory`。
- **表示スプライト数を数えるなら停止マーカ(Y=終端値)以降を無視**（全 32 スロット走査は残骸を誤カウント）。
- **Tcl ヒアドキュメントで `$i` 等がシェル展開・配列誤認されないよう注意**（アドレスだけシェル展開、Tcl 変数は
  エスケープ）。実際に `#$i(...)` が「配列でない」エラーを出した。
- **throttle off は時刻が非決定的**（検証用 insta-clear=無敵でステージが巡回するため、単一フレーム撮影は不安定
  ＝各要素を個別に確認）。スクショ確認は throttle on＋ハートビート方式が確実。
- グローバル追加で番地がずれる → 検証 tcl の前に必ず `build/rom.map`/`.noi` で `_g_*` を取り直す。

## まとめ（次作への一行教訓）

1. **crt0 で _DATA を必ずゼロ化**（リセット残留 state 対策）。
2. **アドレスは毎ビルドで動く**。おかしい値はまずアドレス/スクリプトを疑う。
3. **実プレイ条件（発砲ホールド＋不死 poke）で測る**。idle は過小評価。
4. **微最適化でなく構造的削減**（走査回数・コピー面積・エンティティ数）。
5. **VDP 律速は塗る頻度・面積を減らす**（方式高速化だけでは足りない）。VDP 操作は 1 di/ei 区間に閉じる。
6. **効果対リスクの悪い命令(YMMM・差分発行)は使わない**。コマンドレジスタは毎回書く。
7. **N フレーム毎の一括処理は周期ヒッチの元** → 1件/フレームに分散。
8. **状況証拠で決め打ちせず再現して確定**。測定スクリプトを疑う。市販 ROM が動くなら自分のバグ（背理法）。
9. **旧版/文献を当たる**。「できない」で止めない。旧版機能は落とさない。
10. **openMSX は UUID で絞る・timeout 必須・グローバル設定は事前確認**。実機依存バグは C-BIOS をすり抜ける。
11. **計測器がゲーム状態(VRAM)を破壊し得る**。「実機だけ/Z80 で再現せず」を R800/エミュ固有と決め打ちせず、
    **まずデバッグ処理・計測器を疑う**（炎 BG 化けの真犯人はプロファイラだった）。
12. **VDP-CPU 並列は VRAM 非接触の純 CPU の裏だけ**。直書き(ent_draw_all)と VDP コマンドを重ねない。
13. **CPU 律速の正体は ROM フェッチ**（R800 でも ROM は約3.8×遅い）。最重ホットは RAM 実行化(hot_ram/§4-3)で
    初めて R800 の速さを取り切れる。**RAM 実行の固定枠(HOT_CAP)はビルド時ガードで縛る**（超過は無警告で暴走）。
14. **速くしたら速度がフレームレート依存でないか確認**（固定タイムステップで守る）。**音はメロディ最優先**＝
    効果音はベース/ドラム側 ch へ。
15. **ヘッダ依存を全 include に張る**（stale-object バグ回避）。構造体を触ったら `make clean`。
