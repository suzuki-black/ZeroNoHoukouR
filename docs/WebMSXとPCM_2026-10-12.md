# WebMSX と turboR PCM — 問題・原因・対応のまとめ（2026-10-12）

「真 零の咆哮」（MSX turboR 専用・8メガビットの ASCII8 メガROM）を WebMSX で動かしたときの PCM まわりの問題を、
別の検討（別の AI への相談）に渡すためにまとめたもの。**確認済みの事実**と**未確認・推測**を分けて書く。
**2026-10-18 追記**: 2-2 は原因が分かり、WebMSX 用の ROM を別に作って対応した（§5-2）。§5 の推測はそのときのまま残してある。

---

## 1. 本作の PCM の作り（前提）

- 鳴らすもの: 面中の**スネア**（128B・約 32ms）と、**叫び 3 語**（「乾坤一擲」「敵撃破」「総大将撃破」。bank64〜66）。
- サンプルレート **3996Hz**。BIOS の PCMPLY は使わない（前景で止まるので、ゲームを止めずに鳴らせない）。
- **ポート A4h へ 1 バイトずつ直接書く**。A5h には 03h（BUFF=ダブルバッファ、MUTE 解除）を書いておく。
  書いた値は PCM の次の刻み（15.7kHz）で出る。
- **書く時刻はシステムタイマ（E6h/E7h、1 カウント約 3.911µs）で測る**（「前の予定＋64 カウント」）。
- **書くきっかけは走査線割込み**（R#19 / S#1 の FH）。鳴っている間だけ、次のサンプルの時刻に当たる行にも走査線割込みを張る
  （毎フレームの合図＝212 行目の割込みや、画面分割の割込みと 1 本の R#19 を共有し、近い方を張る）。
- 鳴らせない機械では何もしない（PCM を入れる前と同じ動き）。設定メニューで `PCM SOUND` = OFF / ON / ONLY。
- 詳細: [PCM調査_2026-10-07.md](PCM調査_2026-10-07.md)、[ARCHITECTURE.md](ARCHITECTURE.md) §3.13・§3.16。
- **A4h/A5h の読み書きの出典**: openMSX `src/sound/MSXTurboRPCM.cc`（`peekIO`: A4h は `bit 0-1 15.700kHz counter / bit 2-7 not used`、
  A5h は BUFF / MUTE / FILT / SEL / SMPL ほか）、OCM の `tr_pcm.v`。turboR のテクニカルデータの該当箇所は未確認。

### 起動時の「PCM が使えるか」の判定
| 版 | 判定 | 置き場 |
|---|---|---|
| v0.4.0〜v0.4.5（公開済み） | **システムタイマ（E6h）の下位バイトが動くか**だけ | `src/banked/coldsetup.c` の `pcm_detect` |
| ローカルの修正 `9c26423`（**未プッシュ**・未リリース） | 上に加えて、**A4h を読んで値が一度でも変わるか**（PCM の刻みで回る 2bit カウンタ） | 同上 |

## 3. 原因（2-1。確認済み）

1. **本家 WebMSX（GitHub `ppeccin/WebMSX` master＝Release 6.0.8, 2026-03-10）は turboR の PCM を鳴らさない**。ソースで確認:
   - `src/main/msx/machine/DeviceMissing.js`: `IGNORED_PORTS` に `0xa4, 0xa5 // tR Internal PCM`。未実装ポートは**読むと 0xFF、書くと捨てる**。
   - `src/main/msx/miscdevices/TurboRDevices.js`: BIOS の **PCMPLY / PCMREC を横取り（`patchPCMBIOS`）しているが、中身は C フラグを立てて
     「失敗」を返すだけ**。BIOS 経由で鳴らすソフトも鳴らない。
   - 同ファイルで **システムタイマ E6h/E7h は実装されている**（16bit カウンタ）。
2. 本作の判定（v0.4.0〜v0.4.5）はシステムタイマしか見ていなかったので、**WebMSX でも「PCM あり」**になっていた。
3. そのため、スネアの拍ごとに**鳴らない PCM のためのサンプル用の走査線割込み**を張っていた（A4h への書き込みは捨てられる）。
4. 3 面の中ボスは、背景に描いた艦を**画面を 32 行ずつ 7 本の帯に分けて帯ごとに横スクロール（R#26/R#27）**して動かす。
   1 フレームに分割の割込みが 6 本あり（実測で毎フレームの合図と合わせて 7 本・間隔約 32 行）、WebMSX の限界の際どい所（過去の実測: WebMSX は帯 6 本・間隔 29 行まで、
   実機 turboR は帯 8 本・間隔 22 行まで。[raster.h](../src/include/raster.h) の RAS_MAX のコメント）。
5. そこへサンプル用の割込みが混ざると、WebMSX では帯の切り替えが遅れる・抜ける → 艦の帯に別の帯の横ずれが一瞬当たり、艦が左右へ跳ぶ。
   openMSX では間に合うので出ない（実機は未確認）。
6. **実測（2026-10-12・openMSX・3 面の中ボスの間・走査線割込みの入口を数えた）**:

   | | 1 フレームの割込み | 割込みどうしの最小間隔 |
   |---|---|---|
   | PCM OFF | ほぼ毎フレーム 7 本（分割 6 本＋毎フレームの合図） | 約 32 行 |
   | PCM ON（スネアが鳴っている 191 フレーム） | **25〜47 本** | **5〜9 行** |

   スネアの間は、帯の分割の間にサンプルの割込みが 4〜8 行おきに挟まる。

## 4. 対応（2-1）
- `9c26423`（**ローカルのみ・未プッシュ**）: 起動時の判定に「**A4h を読んで値が一度でも変わるか**」を足した。
  - 実機と openMSX: A4h の下位 2bit は PCM の刻み（15.7kHz）で回るカウンタ（openMSX `src/sound/MSXTurboRPCM.cc` の `peekIO`:
    `bit 0-1 15.700kHz counter / bit 2-7 not used`）。OCM（FPGA 互換機）の `tr_pcm.v` も同様。→ 「あり」。
  - 本家 WebMSX: 常に 0xFF → 「なし」→ PCM を切り、サンプル用の割込みも張らない。ちらつきは消えるはず（**WebMSX では未確認**）。
  - openMSX で「あり」（`g_pcm_hw=1`）のままになることは確認済み。
- **リスク（未確認）**: 実機で A4h のカウンタが回らない場合、実機でも PCM が「なし」になりスネアと叫びが鳴らなくなる
  （ゲームは止まらない。PCM OFF と同じ動きになる）。**実機（2026-10-12 以降）で確かめてからプッシュする予定**。
  - 判定は**起動時・A5h を一度も書く前**（A5h はゲームが鳴らし始めるとき `pcm.s` の `_pcm_start` で初めて 03h を書く）。
    順序は「E6h（タイマ）→ A4h」で固定。A4h は「値が一度でも変わるまで、最大 20000 回読む」＝少なくとも 2 種類の値を見たら「あり」。
  - 判定の所要時間（openMSX）: 約 2.1ms（スネアの素材を RAM へ写す分を含む）。PCM の無い機械でも最大約 0.1 秒・起動時 1 回。
- **判定を直しても、PCM を鳴らすエミュレータ（A4h を実装したもの）では、上の「分割の間にサンプルの割込みが挟まる」構造は残る**。
  そこで次の対策も入れた（ローカル・未プッシュ）:
  - **画面分割が 7 本以上ある間（`g_ras_n >= 7`）はスネアを鳴らさない**（`pcm.s` の `_pcm_snare`。常駐 6B）。3 面の中ボスは 8 なので
    その間はスネアが鳴らない（PSG と FM のドラムは鳴る）。ふだんの戦艦の場面は 2 で影響なし。衝撃波が大きい瞬間（最大 7）も鳴らない。
  - 対策後の実測（openMSX）: 中ボスの間は割込み 7 本・間隔約 32 行（PCM OFF と同じ）、スネアの開始 0 回。中ボスの後はスネアが 517 回鳴り、戻る。
  - 叫び 3 語が鳴るのはゲーム開始（`scene.c`）と撃沈の結果画面（`gen_planes.c`）だけで、中ボスの最中に鳴る経路は無い。

## 5. 2-2（file-hunter の WebMSX でブツブツ鳴る）について — 2026-10-12 時点の推測（原因と対応は §5-2）

### 分かっていること
- file-hunter のページのフッタは「WebMSX by Paulo Peccin」と webmsx.org へのリンク。**サイトで動いている WebMSX が本家と同じ版か、
  PCM を足した別の版かは確認できていない**（ページの内容からは埋め込みのスクリプトが見えなかった）。
- 本家 6.0.8 のソースには、turboR PCM（A4h/A5h の直接書き込み・BIOS の PCMPLY のどちら）を鳴らす実装は無い。
  本家の README も turboR の節で「There is no PCM and MIDI support yet」と書いている（音源の一覧の「PCM」は、PCM を積んだ
  カートリッジ＝ソースの `CartridgeMajutsushi` / `CartridgeSynthesizer` のこと）。
  したがって「PCM 対応している」なら、**本家より新しいか、別に改造した WebMSX**、または PCM カートリッジのことを指している可能性がある。

### file-hunter の WebMSX と webmsx.org の WebMSX の比較（2026-10-12 に両方のスクリプトを取得して確認）
| | webmsx.org | file-hunter.com/MSX/ |
|---|---|---|
| 置き方 | HTML 1 枚にスクリプトを埋め込み（約 5.3MB） | 自前の `https://www.file-hunter.com/assets/wmsx.js`（約 5.8MB）を読み込む |
| 版数（スクリプト内の `VERSION`） | **6.0.8** | **6.0.8** |
| 未実装ポートの一覧 | `…,147,164,165,184,…`（**A4h/A5h を含む**） | `…,147,184,…`（**A4h/A5h が外されている**） |
| turboR PCM の装置 | 無し | **`wmsx.TurboRPCM` が足されている**（A4h/A5h の入出力を接続） |
| BIOS の PCMPLY/PCMREC | 横取りして「失敗」を返す | 同じ（コードが一致） |

→ **file-hunter は本家 6.0.8 に turboR PCM の装置を足した改造版**。「自分のサイトの WebMSX は PCM 対応」は、この A4h/A5h の直接書き込みのこと。
BIOS の PCMPLY を使うソフトは file-hunter 版でも鳴らない（コードが本家と同じ）。

`wmsx.TurboRPCM`（圧縮されたコードから読み取った動き）:
- **A4h を読む**: 前回 A4h に書いてからのバスのサイクル数 ÷ 228 の下位 2bit（3.58MHz ÷ 228 ≒ 15.7kHz）。**A4h に書くたびに 0 に戻る**。
- **A4h に書く**: MUTE でなければ**その場で**値を音に反映する。**A5h の BUFF（ダブルバッファ＝次の刻みで出す）は使っていない**。
- **A5h を書く**: bit1（MUTE）と bit4（SMPL）を扱う。読むと bit7 に比較器の結果、下位 5bit に書いた値。
- 音は `PCM8BitAudio`（PCM カートリッジと同じ部品）へ「今の値」として渡し、CPU クロック ÷ 32 = 112,005Hz で拾われる（`AudioSignal` の `audioClockPulse`）。
  → 書いた時刻どおりに音になるはずで、**拾い方そのものは途切れの原因になりにくい**。

本作との関係:
- `9c26423` の判定（A4h の値が変わるか）では、file-hunter 版は**「PCM あり」**になる（書かなくてもカウンタは回る）。v0.4.5 も「あり」。
- したがって file-hunter 版では、本作は PCM を鳴らそうとする。3 面の中ボスのちらつきは、スネアを止める対策（§4）で避けられる。
- **ブツブツの一番の容疑**: 本作は 3996Hz を出すため、鳴っている間は**約 4 行おきに走査線割込み**を張る（3 面の中ボスの測定で間隔 5〜9 行）。
  WebMSX は分割の実測で**間隔 29 行より狭い割込みを取りこぼす**。サンプルの割込みが遅れる・抜けると、本作は 1ms 以上遅れたら予定を今へ
  合わせ直すので、音が途切れ途切れになる。→ 調査項目 3-2 のテスト ROM B（割込みで刻む）と C（割込みを使わずタイマだけで刻む）の
  比較で確かめられる（B だけ荒れれば、この容疑で確定）。

### 推測（確かめる必要あり）
- その WebMSX が A4h/A5h を実装していて、本作の方式（走査線割込みで 1 バイトずつ・時刻はシステムタイマ）で鳴らすと、
  エミュレータ側の次のどれかが実機と違えば、**途切れた（ブツブツの）音**になりうる:
  1. **A5h の BUFF（ダブルバッファ）の扱い**: 本作は「書いた値は次の 15.7kHz の刻みで出る」前提。即時に出す実装や、BUFF を無視する実装だと、
     出る時刻がずれて音が荒れる。
  2. **A4h への書き込みを音声のサンプルとして拾う方法**: 書き込みの時刻ではなく、音声フレームごとの最後の値だけを拾う実装だと、
     3996Hz の書き込みが間引かれて崩れる。
  3. **走査線割込みの時刻の正確さ**: サンプルを出すきっかけが走査線割込みなので、割込みが遅れる・抜けるとサンプルが欠ける
     （2-1 と同じく WebMSX は分割に弱い）。本作は 1ms 以上遅れたら予定を今へ合わせ直すので、欠けは「途切れ」として聞こえる。
  4. **システムタイマ（E6h/E7h）の進み方**: 実機は約 3.911µs/カウント。速さが違うと、サンプルの間隔（64 カウント）が変わる。
- `9c26423` の判定は「A4h が読めて値が変わるか」なので、**A4h のカウンタまで実装した WebMSX では「PCM あり」になり、
  この版でも鳴らそうとする**（ブツブツの原因が上のどれかなら、修正版でも変わらない）。

### 切り分けに要る情報（ユーザー側で確認できるもの）
- 試した ROM の版（リリースの v0.4.5 か、ローカルの修正版か）。
- ブツブツ鳴るのはどれか: ゲーム開始の「乾坤一擲」/ 面中のスネア / 結果画面の「敵撃破」。
- 設定で `PCM SOUND` を OFF にするとブツブツが消えるか（消えるなら PCM の音、消えないなら別の音）。
- file-hunter のサイトで使っている WebMSX の版（画面のメニューや About に版数が出るか）。

## 5-2. 2-2 の原因と対応（2026-10-17〜18。解決）

### 計測のしかた
- 本家 WebMSX 6.0.8 の **C-BIOS 版**（BIOS を含まない公開物）に、実機（FS-A1ST）から吸い出した BIOS を読ませて turboR を組み、
  file-hunter 版と同じ動きの PCM の口（A4h に書いた値をその場で音にする）を足した。手元の localhost だけで動かした。
- JavaScript で、A4h への書き込み・R#19/R#23 の書き込み・割込みの線の上げ下げを、バスのサイクルと VDP の表示行つきで記録した。

### 分かったこと
- 面の中のスネア（129 サンプル）は欠けずに出る。**ゲーム開始の叫び（乾坤一擲）だけ**、最初の約 200 サンプルの後、
  3〜4 サンプルごとに丸 1 フレーム抜けていた（5 秒で 115 回。1 フレームに 3〜4 サンプルしか出ない）。
- 本作は次のサンプルの行を、システムタイマから見積もった「いまの行」の 4 行以上先に張る。WebMSX では**張った時点の余裕が
  0〜3 行**しかなく（openMSX では常に 2〜3 行）、2 割強は「いまの行」か「もう過ぎた行」を張っていた。過ぎた行の割込みは
  1 フレーム後まで来ない。
- 合図の割込みの入り（212 行目）・システムタイマの速さ・見積もりの式は、WebMSX でも正しかった。違いは、割込みが
  上がってから CPU が処理を始めるまでの遅れ（WebMSX は実機・openMSX より 1〜1.5 行遅い）で、重い準備の間に鳴る叫びで
  余裕が尽きていた。

### 対応
- **WebMSX 用の ROM を別に作る**（`make webmsx` → `WEBMSX.ROM`。リリースに `*-webmsx.rom` として添付）。`hot_pcm.s` の
  `.if WEBMSX` の中で、次のサンプルを待って出す範囲を 1 行 → 3 行、張る行の最小を 4 行先 → 6 行先にした。
  通常の ROM（実機・openMSX 用）は 1 バイトも変えていない（割込みの中で待つ時間が増えるので、実機の重い場面には入れない）。
- 手元の WebMSX で、叫びの 4120 サンプルが抜けなく出た（openMSX と同じ数）。スネア・ゲームの速さ（900 フレームで合図 900 回）も変わらない。
- ユーザーが file-hunter の WebMSX で WebMSX 用の ROM を聞き、叫びとスネアが聞き取れることを確かめた（2026-10-18）。
- 実機では通常の ROM で叫びとスネアが鳴ることも確かめた（`9c26423` の A4h の判定が実機で「あり」になる）。
