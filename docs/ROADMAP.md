## 1. 引き継ぎ時点で判明した構造的な問題

### 1-1. ★最重要: 一番熱いコードが、一番遅い側に落ちている

§4-3 の RAM 実行（`ramexec.c`）が高速化するのは **page1 = 0x4000–0x7FFF の 16KB だけ**。
常駐は 24KB あるので、**0x8000–0x91DB の約 4.5KB はカートリッジ ROM フェッチのまま**であり、
そこに居るのが実際には次の面々である（`build/rom.map`）:

| 番地 | 中身 | 実行頻度 |
|---|---|---|
| 0x8C07 | `stage_update`（1,330 B） | **毎フレーム。ゲームループ本体** |
| 0x8131 | `burn_add`（〜1,836 B） | 破壊イベント毎 |
| 0x885D | `stage_init`（938 B） | 面開始 |
| 0x9149–0x91DB | `__mulint` / `__divuint` / `__divsint` / `__moduint` | **毎フレーム多数回** |

どの関数が 0x8000 を越えるかは `Makefile` の `RESIDENT_RELS` の並び順で決まっているだけで、
**熱さでは選ばれていない**。docs の「R800 の ROM フェッチは RAM 実行の約 3.8 倍遅い」が正しいなら、
ここは演出予算に直結する取りこぼしである。**ただし本件は未測定の仮説であり、実機計測で確かめてから
直したと言うこと。**

### 1-2. 派手演出を置く RAM 枠が、もう無い

`hot_ram` の残り 113 B、常駐の残り 3,527 B。設計メモの A〜F（パレット・歪み・弾幕・アフィン・粒子）は
すべて「RAM 常駐の重い計算」なので、**現状は入れる場所が無い**。演出コードを演出ごとに RAM へ
載せ替える「エフェクト・オーバレイ・ローダ」（`hot_load` のシーン単位版）が前提として要る。

### 1-3. turboR 性能を検証する手段（決定済み）

openMSX 21.0 には `turbor.xml` があるが turboR システム ROM が未設置のため、この Mac では
**Z80 / MSX2+ でしか動かせない**。
→ **方針決定: 正しさは openMSX（Z80）、turboR 性能は実機 turboR ＋ `make DEBUG_PROF=1`（S1990
タイマの区間計測 `PF_*`）で測る。** 性能に関わる変更は **必ず前後の A/B 実測をセットで残す**。

### 1-4. 小さな不整合（順次片付ける）

- `config.mk` の `ROM_SIZE = 0x20000`（128KB）は死んだ値。実体は `tools/rompack.mjs` の
  `ROM_SIZE = 0x40000` にハードコード＝真実が二重。
- `ARCHITECTURE.md` が参照する `HANDOFF §1/§2/§7` は本リポジトリに存在しない（前作の文書）。
- `docs/仕様書.md` は旧作の仕様のまま。タイトル画も「零の咆哮 改」のまま。
- プロジェクト側 `CLAUDE.md` が未作成（監査項目・openMSX 運用・バージョン保持ファイル一覧）。

## 2. 作業計画

### P0 — 基盤（演出を載せる前にやる）★現在ここ

1. **RAM 実行の適用範囲を、熱さで決め直す**（§1-1）。→ **(a) を実装し、実機 A/B で効果を確認済み（完了）。**
   実機 turboR 実測で **COMPUTE −941µs/frame (−9.8%)**、COLLIDE −10.8% / DRAW −8.9% / UPDATE −5.3% /
   AA −2.1%、CMDWAIT は不変。数表と但し書きは [性能と高速化 §3-A2](性能と高速化.md)。
   ★同時に **CMDWAIT ≈ 14.1ms/frame > COMPUTE 8.7ms** が実測され、**律速が VDP であること**が確定した。
   演出は必ず「重い計算・軽い出力」で作る、という本企画の芯が数字で裏付けられた。
   - **(a) 機構で直す（採用）**: §4-3 を **page2(0x8000–0x9FFF) にも拡張**し、常駐 24KB 全体を
     RAM 実行にした。出入口は `ramx_use_ram()`/`ramx_use_cart()` の1対に集約（page1 と同じ区間・
     同じ規律）。リンク順に依存しない恒久的な解。詳細は [ARCHITECTURE §3.9](ARCHITECTURE.md)、
     踏んだ地雷は [苦労と教訓 §5-1](苦労と教訓.md)。
     - openMSX で確認済み: `g_ramx_ok=1 / g_ramx2_ok=1`、`slotselect` でホット区間内のみ
       **0x4000・0x8000 が共に RAM スロット**、区間外は cart。130 秒の実プレイ回帰で破綻なし。
     - **未検証（実機のみ）**: 速度がどれだけ改善するか。`make clean && make DEBUG_PROF=1` と
       `make clean && make DEBUG_PROF=1 NO_RAMX2=1` の2本を実機で走らせ、`PF_*` の区間 tick を
       比較する。**この数字が出るまで「速くなった」とは書かない。**
   - **(b) 並びで直す（不採用）**: `RESIDENT_RELS` の順とファイル内の関数順を並べ替え、
     冷たいものだけ 0x8000 以降へ追い出す案。モジュールを足すたびに崩れるので恒久解にならない。
2. **エフェクト RAM オーバレイ機構**（§1-2）→ **完了**。
   ★**page2 を RAM 化している間、0xA000-0xBFFF が丸ごと遊んでいた**のを使う。§4-3 の page2 RAM 実行は
   空きセグメント seg5(16KB)を page2 へ割り当て、その**下位 8KB にだけ**常駐 bank2 の複製を置いている。
   page2 は 0x8000-0xBFFF なので上位 8KB が未使用のまま残る。ここへ演出コードを載せる。
   - **追加の RAM 消費ゼロ**(既に確保済みセグメントの空き) / **RAM 実行なので R800 で全速**
     (バンク実行の 3.84 倍) / **8KB まるごと**使える
   - 制約と作法は [overlay.h](../src/include/overlay.h)。要点は「ホット区間の中でしか呼べない」
     「オーバレイ側から data_read/bcall は不可」「常駐の関数/データは通常どおり呼べる」。
   - 最初の利用者＝CPU 弾幕の本体。**常駐 23726B → 22397B(+1329B)**、ovl.bin = 1491/8192B。
2-B. **常駐リクレイム（P0-2 の続き・都度）**: 演出を常時オンにしたところ `DEBUG_PROF` ビルドが
   常駐 24KB を 998B 超過した（rompack が検出）。面開始で 1 回しか走らない cold code を追い出して回収:
   戦闘機 8 方向の手続き生成（約900B）→ **bank19**(`gen_planes.c`)、弾幕の斉射/流し込み → オーバレイ。
   現況は **通常 21,516B（残り 3.0KB）/ DEBUG_PROF 24,448B（残り 128B）**。
   ★DEBUG_PROF が 128B しか余っていない。次に常駐へ足す前に、また何かを追い出すこと。
3. **フレームレート方針の確定**: 現状 30fps 固定（2 VBLANK 待ち）で 1 VBLANK 分を捨てている。
   **方針＝30fps 据え置きのまま、空き VBLANK を演出に全振り**（速度定数の再調整が不要でリスクが低い）。
4. **掃除**: `ROM_SIZE` 一本化、`HANDOFF` 参照の解決、プロジェクト `CLAUDE.md` 作成。

### P1 — 見せ場（設計メモ §2 の推奨順 A→B）

★③ 弾幕と ★A パレットエンジンは**完了・常時オン**（フラグを畳み済み）。到達点:
`raster.c`(R#19/FH の画面分割) → スプライト表2セット(R#5 切替で総数32の壁を破る) →

海のシマー)。実測で同時生存20発・表示24発、パレットは 16色全書換でも 0.32ms。

**ビルドフラグの方針**: 実機で確認が取れた演出はフラグを持たず常時オン。ビルドフラグは
計測/切り分け用だけ(`DEBUG_PROF` / `DEBUG_FPS` / `NO_RAMX2` / `DEBUG_NOSEA` / `DEBUG_NOENT`)。

★メガクラッシュも**完了・常時オン**。B ボタンで発動(残数は画面下に棒の本数で表示)、スクロールも
BGM も止めて ①地鳴り(揺れ＋低いノイズ) → ②**手続き生成した稲妻**を3回(中点変位＋分岐 / 苦労と教訓 §11)
→ ③**画面幅の水の壁**が加速しながら駆け上がる → ④画面上の敵弾だけ消して BGM を**続きから**再開。
稲妻は V9938 の LINE。津波は **スプライト拡大(R#1 MAG)で1枚32x32** にした 8列×4段=32枚＝
256×128px(1走査線ちょうど8枚)。絵は `tools/gen_wave.py` が生成し、焼く前にプレビューできる。
「止めてよい」と仕様で決めたので 30fps の予算に縛られない(クラッシュ中だけ 60fps で回す)。
openMSX(Z80機)実測で 3.8 秒。実機 turboR は CPU が数倍速いのでこれより短い。

残件: 3帯目(セットC=VRAM 0x6C00/0x6E00, R#5=0xDF)で表示枠を 24→36 へ。

## 2-B. 大型演出 3 案の実現可能性（実測定数で判定・2026-09-11）

判定の土台は [性能と高速化 §0-0](性能と高速化.md) の実測定数
（**VDP 204 B/ms・残枠 3.9 KB/frame**）。**MSX コミュニティの一次情報に当たった結果、
当初「帯域的に不可能」と判断した 3 案は、いずれも前提が誤っていた**ので記録を残す。

### ① 縦の多重スクロール → **可能（ただし「左右」ではなく「レイヤ」）**

- **誤っていた前提**: 「毎フレーム全画面を再合成しなければならない(27KB/frame)」。
  実際は **償却できる**。[artrag/Parallax_scrolling_MSX2](https://github.com/artrag/Parallax_scrolling_MSX2)
  は screen5 で 2 層パララックス＋8方向スムーススクロールを**素の MSX2(Z80 3.58MHz)**で実現している。
- **機構**: 画面を 16×16 ブロックで構成し、**16 フレームかけて 1 列ずつ裏ページに再構築** →
  完成したら表裏入替。その間の 1px の動きは HW スクロール(R#23/R#26-27)が担う。
  背景は前景の **15/16 速度**（16 はスクロールレジスタのステップ数由来）。スプライトは全部ゲーム用に空く。
  VRAM 4 ページ使用（2=ダブルバッファ / 2=両レイヤのブロック素材）。
- **コスト**: 27KB ÷ 16 = **1.7 KB/frame = 8.3 ms**。残枠 3.9KB に収まる。現行の海+艦描画
  (2.9KB/frame)と**置き換える**形なので差し引きでは軽くなりうる。
- **障壁は帯域でなく VRAM 設計**: 本作は page0=スプライト/炎, page1=表示リング, page2-3=艦バッファB で
  128KB を使い切っている。艦を「ブロックの集合」として持ち直す改造が要る。
- **残る本当の制約**: **画面を縦に割って左右で別速度は不可**（R#23 は画面全体に効く単一レジスタ。
  community も "A clean split of the screen in left and right parts is not possible on V9938/V9958"）。
  横帯に割る screen split は可能。

### ② 戦艦級の疑似回転・拡大縮小 → **サイズで線が引ける**

- **誤っていた前提**: 「R800 が毎ピクセル計算 → VRAM へ転送」という形だけを検討していた。
  MSX2 の定石は **事前生成コマを VRAM に置き、VDP コマンドで貼る**。screen5 は 4 ページ=128KB ある。
- G4 の「1 バイト = 2 ピクセル」で**横 2 倍は無料**（半解像度で作れば表示は倍）。

| 対象 | バイト数 | 所要 | 判定 |
|---|---|---|---|
| 48×64 のコマ | 1,536 B | 7.5 ms/frame | 30fps で可 |
| 64×100（表示 128×200） | 3,200 B | 15.7 ms/frame | 15fps なら可 |
| 戦艦級 128×200 実解像度 | 12,800 B | 63 ms/frame | **不可（2fps 相当）** |

- ★**見落としていた強い手: [screen split で R#23 を行ごとに変える](https://map.grauw.nl/articles/split_guide.php)**。
  R#23 は **mid-frame 変更が即時反映される非シームレス・レジスタ**＝走査線ごとに「VRAM のどの行を
  表示するか」を選べる。**縦方向の拡大縮小・うねり・傾き・沈み込みが VRAM 転送ゼロで作れる**
  （設計メモ §2-B の全画面ディストーションの相当部分が、コピーでなくレジスタ書換で実現できる）。
  - 作法: R#23 を split で変えたら **R#19 を再計算**（split 行は画面行でなく VRAM 行 0 起点で数える）。
    変更前に E1(R#0 bit4)を落として S#1 を読む。
  - 制約: HBLANK 中に書けるのは **レジスタ 4 本（間接アクセスなら 8 本）＋パレット 8 エントリ**。
    212 行全部で割り込むと CPU をほぼ食い潰す（split guide が警告）→ **帯単位に限定するのが現実的**。
- **役割分担の結論**: 回転そのもの＝事前生成コマ＋HMMM / 縦の変形＝R#23 split。

### ③ スプライト限界を超える弾数 → **可能。3 案で最も安い**

- **誤っていた前提**: 「32 枚はハード上限だから終わり」。**回避技法が確立している**。
- **スプライト分割(sprite split / line interrupt)**: R#19 に分割行、S#1 の FH を見る（または R#0 の
  E1 で割り込み）。分割行で SAT を書き換え**同じ 32 枚を別の帯で再利用**。2 箇所分割で **48 枚**、
  分割を増やせばさらに。**Space Manbow が実ゲームで使用**。
- **別解**: SAT を VRAM に 2 つ持ち R#5/R#11 を切替（正順・逆順で並べ実効 16 枚/走査線をフレーム交互）。
- **併用**: 1 パターンに複数弾を描くクラスタパターン（`run_fire` の RING/AIMFAN は元々編隊で出る）。
- **コスト**: SAT 全書換 128B = 0.64ms。2 分割で 3 セット使っても **1.9 ms/frame**。
  クラスタパターン 8 枚再生成 = 256B = 1.3ms。→ 合計 3ms 程度で **48〜96 発相当**。
- **残る本当の制約**: **1 走査線 8 枚はハード制約で回避不可**。横一線の壁は出せない。
  → 弾幕は**縦に散る形（リング・螺旋・雨）**に寄せる。
- 弾の**計算**は純 RAM 演算で VDP コスト 0＝「重い計算・軽い出力」の理想形。**制約は表示だけ**。

## 3. この計画で守る規律

- **性能の主張は実機計測とセットでのみ書く**（§1-3）。openMSX の数値は正しさの検証にのみ使う。
- **「何を計算するか」より「何を VRAM に書かないか」**（設計メモ §3）。演出の出力は
  パレット・スクロール・少数スプライト・低頻度/小領域の VDP コマンドに押し込む。
- **失敗と見送りも残す**（前作 `性能と高速化.md` §3-D の方式）。効かなかった最適化こそ次への資産。
